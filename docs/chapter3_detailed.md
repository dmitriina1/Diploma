## 3.1. Требования к информационной системе

### 3.1.1. Процесс выявления и формализации требований

Проектирование информационной системы для автоматизированной подготовки к IT-собеседованиям представляет собой многоэтапный процесс, начинающийся с глубокого анализа предметной области и завершающийся детализированной технической спецификацией. В рамках данного исследования процесс выявления требований проводился в соответствии с рекомендациями стандарта IEEE 830-1998 (Software Requirements Specification) и принципами итеративной разработки.

**Источники требований.** Формирование требований базировалось на следующих источниках:

1. **Анализ предметной области.** В ходе исследования предметной области (глава 2) были выявлены характерные особенности подготовки к IT-собеседованиям: многообразие форматов вопросов (технические, алгоритмические, системные, поведенческие), необходимость повторения и закрепления знаний, потребность в структурированной навигации по темам и уровням сложности.

2. **Анализ конкурентных решений.** Исследование существующих платформ (Glassdoor, LeetCode, InterviewBit, Pramp, easyoffer.ru) позволило определить базовый набор функций, ожидаемых пользователями, а также выявить незаполненные ниши — в первую очередь, отсутствие интеграции видеозаписей реальных собеседований с автоматическим извлечением вопросов.

3. **Потребности целевой аудитории.** Целевой аудиторией системы являются:
   - IT-специалисты, готовящиеся к смене работы (возраст 22–35 лет, уровень владения технологиями — от junior до senior);
   - Студенты технических специальностей, готовящиеся к первому трудоустройству;
   - HR-специалисты и технические лидеры, формирующие банки вопросов для собеседований.

4. **Технические ограничения.** Разработка ведётся для развёртывания на серверах с ограниченными ресурсами (без GPU), что накладывает требования на оптимизацию вычислительно-интенсивных компонентов (транскрибация речи, семантический поиск).

**Методика приоритизации.** Требования классифицированы по методу MoSCoW:

| Приоритет | Описание | Количество требований |
|-----------|----------|----------------------|
| Must have | Критически необходимые функции | 15 |
| Should have | Важные, но не блокирующие | 8 |
| Could have | Желательные дополнения | 5 |
| Won't have (v1) | Отложены на будущие версии | 4 |

К категории Must have отнесены: обработка видео, транскрибация, извлечение вопросов, каталогизация, базовая фильтрация и административная панель. К категории Should have — тренажёр SM-2, UGC-функции, mock-собеседования. К Could have — интеграция с HeadHunter, тестовые задания. К Won't have (v1) — полнотекстовый поиск с ранжированием, рекомендательная система, авторизация пользователей.

**FR-1. Обработка видеоматериалов с собеседованиями.**

Данное требование является ключевым отличием разрабатываемой системы от конкурентных решений. Система должна обеспечивать полный автоматизированный pipeline извлечения структурированных данных (вопросов, ответов, таймкодов) из неструктурированного источника (видеозаписи собеседования).

*FR-1.1. Мультиплатформенная загрузка видео.*

Система должна поддерживать загрузку видеоконтента с не менее чем 6 популярных видеоплатформ. Выбор платформ обоснован анализом распределения русскоязычного контента с IT-собеседованиями:

| Платформа | Доля контента | Обоснование |
|-----------|--------------|-------------|
| YouTube | ≈60% | Крупнейшая мировая площадка, основной источник IT-контента |
| VK Video | ≈20% | Крупнейшая российская площадка, активно развивающийся видеохостинг |
| Rutube | ≈10% | Российская альтернатива YouTube, растущая доля контента |
| OK.ru | ≈5% | Популярная российская социальная сеть с видеохостингом |
| Dailymotion | ≈3% | Международная площадка с дополнительным IT-контентом |
| Vimeo | ≈2% | Площадка для профессионального видеоконтента |

Для каждой платформы должно быть реализовано:
- Автоматическое определение платформы по URL (regex-паттерны);
- Извлечение уникального идентификатора видео;
- Загрузка аудиодорожки с конвертацией в формат MP3 (192 kbps);
- Загрузка автоматических субтитров (при наличии) в формате WebVTT;
- Платформо-специфичные настройки (ограничения по размеру, формату, таймаутам).

Платформа VK Video требует особого подхода из-за технических ограничений:
- Ограничение размера загружаемого файла: не более 100 МБ;
- Ограничение длительности видео: не более 60 минут;
- Использование пониженного качества аудио для ускорения загрузки;
- Увеличенные таймауты соединения (60 секунд вместо стандартных 30).

*FR-1.2. Автоматическая транскрибация речи.*

Система должна преобразовывать аудиодорожку видеозаписи в текст на русском языке с использованием нейронной модели распознавания речи. Требования к качеству транскрибации:

- WER (Word Error Rate) не более 15% для русской речи в условиях чистого аудио;
- Поддержка непрерывных аудиозаписей длительностью до 120 минут;
- Генерация таймкодов (временных меток) для каждого сегмента транскрипции;
- Поддержка VAD (Voice Activity Detection) для пропуска участков тишины и фонового шума;
- Автоматическая расстановка пунктуации (критически важно для идентификации вопросительных предложений).

Модель транскрибации должна оставаться резидентной в памяти контейнера после загрузки, исключая повторную загрузку ~3 ГБ модели при каждом запросе. Это существенно сокращает задержку от момента получения задачи до начала транскрибации.

*FR-1.3. Извлечение вопросов и ответов через LLM.*

Из полученного транскрипта система должна автоматически выделять вопросы интервьюера и соответствующие ответы кандидата с помощью больших языковых моделей (LLM). Требования к процессу извлечения:

- Выделение исключительно вопросов интервьюера (не кандидата);
- Для каждого вопроса: определение темы (Backend, Frontend, DevOps, Database, Algorithms, System Design и др.), уровня сложности (junior, middle, senior), таймкода появления;
- Формат вывода LLM — строгий JSON-массив с валидируемой структурой;
- Ограничение входного текста до 50 000 символов для предотвращения превышения контекстного окна модели;
- Температура генерации: 0.3 для извлечения вопросов (детерминизм), 0.7 для генерации ответов (креативность).

Система должна поддерживать не менее 3 LLM-провайдеров для обеспечения отказоустойчивости. При недоступности основного провайдера система автоматически переключается на альтернативный по цепочке приоритетов.

*FR-1.4. Извлечение таймкодов.*

Для каждого извлечённого вопроса система должна определять временную метку (таймкод) его появления в видео. Таймкод сохраняется в двух форматах:
- Строковый формат: `MM:SS` или `HH:MM:SS` (для отображения пользователю);
- Числовой формат: количество секунд от начала видео (для программной навигации).

Парсинг таймкода реализуется функцией, обрабатывающей строки вида `"12:34"` и `"1:02:03"`:

```python
def parse_timecode_to_seconds(tc):
    if not tc:
        return 0
    parts = str(tc).split(':')
    parts = [int(p) for p in parts]
    if len(parts) == 3:
        return parts[0] * 3600 + parts[1] * 60 + parts[2]
    elif len(parts) == 2:
        return parts[0] * 60 + parts[1]
    return int(tc)
```

*FR-1.5. Семантическая дедупликация вопросов.*

При сохранении новых вопросов система должна выполнять двухуровневую проверку на дубликаты:

1. **Точная дедупликация** (case-insensitive): SQL-запрос `SELECT id FROM questions WHERE LOWER(question) = LOWER($1)`. Обеспечивает обнаружение абсолютных текстовых совпадений.

2. **Семантическая дедупликация**: использование векторных представлений (embeddings) модели `all-MiniLM-L6-v2` с порогом косинусного сходства > 0.85. Обеспечивает обнаружение содержательно идентичных вопросов с различными формулировками (например, «Что такое замыкание в JavaScript?» и «Объясните концепцию closure в JS»).

При обнаружении дубликата система не создаёт новый вопрос, а добавляет связь существующего вопроса с текущим видео через таблицу `question_video`, сохраняя таймкод в таблице `question_timecodes`. Таким образом, один вопрос может быть связан с несколькими видеозаписями, что используется для расчёта вероятности появления вопроса на реальном собеседовании.

*FR-1.6. Загрузка локальных видеофайлов.*

Помимо URL-адресов, администратор должен иметь возможность загрузить видеофайл напрямую с локального устройства для обработки. Загрузка реализуется через multipart/form-data POST-запрос на эндпоинт `/api/admin/upload-video-file`. Файл сохраняется во временную директорию TEMP_DIR и далее проходит тот же pipeline обработки, что и видео, загруженные по URL.

*FR-2.2. Многоуровневая фильтрация.*

Вопросы должны поддерживать фильтрацию по следующим параметрам:

| Параметр фильтрации | Тип | Значения | Реализация |
|---------------------|-----|----------|------------|
| Профессия | VARCHAR(100) | 26 slug-ов профессий | JOIN profession_topics |
| Технология (topic) | VARCHAR(100) | Backend, Frontend, Python, Java, ... | WHERE topic = $1 |
| Уровень сложности | VARCHAR(20) | junior, middle, senior | WHERE difficulty = $1 |
| Полнотекстовый поиск | TEXT | Произвольный текст | WHERE question ILIKE $1 |
| Семантический поиск | TEXT | Произвольный текст | FAISS IndexFlatIP |
| Статус одобрения | BOOLEAN | true/false | WHERE approved = $1 |

Фильтры комбинируются по принципу AND. Результаты сортируются по убыванию вероятности (`probability DESC`), затем по дате создания (`created_at DESC`).

*FR-2.3. Расчёт вероятности вопроса.*

На основе статистики встречаемости вопроса в обработанных видеозаписях система рассчитывает вероятность его появления на реальном собеседовании. Формула расчёта:

$$P(q) = \frac{V_q}{V_{total}} \times 100\%$$

где $V_q$ — количество видео, в которых встречается вопрос $q$ (определяется через подзапрос к таблице `question_video`); $V_{total}$ — общее количество обработанных видеозаписей (определяется через `COUNT(*) FROM processed_videos`).

Реализация в SQL:

```sql
UPDATE questions SET probability = (
    SELECT COALESCE(COUNT(DISTINCT qv.video_id) * 100.0 / $1, 0)
    FROM question_video qv
    WHERE qv.question_id = questions.id
)
```

Вероятность пересчитывается:
- При сохранении вопросов после обработки нового видео;
- При объединении дубликатов вопросов;
- При ручном запуске пересчёта администратором (эндпоинт `/api/admin/recalculate-probabilities`).

Данная метрика позволяет пользователям фокусироваться на наиболее часто встречающихся вопросах, оптимизируя процесс подготовки.

*FR-2.4. Семантический поиск похожих вопросов.*

Для любого вопроса система должна находить семантически схожие вопросы с использованием FAISS-индекса. Архитектура поиска:

```
Текст → SentenceTransformer(all-MiniLM-L6-v2) → 384-dim embedding → L2-normalize → FAISS IndexFlatIP → Top-N results
```

Параметры поиска:
- Размерность эмбеддингов: 384;
- Тип индекса: `IndexFlatIP` (Inner Product) — эквивалент косинусного сходства при нормализованных векторах;
- Нормализация: `faiss.normalize_L2()` перед добавлением в индекс;
- Количество возвращаемых результатов: настраиваемое, по умолчанию 10;
- Кэширование: индекс и метаданные сериализуются через `pickle` и хранятся в Redis (ключ `questions_embeddings_cache`).

**FR-3. Обучающие инструменты.**

*FR-3.1. Тренажёр с интервальным повторением (SM-2).*

Система должна реализовывать алгоритм SuperMemo 2 (SM-2), разработанный Петром Возняком в 1987 году, для адаптивного планирования повторений. Выбор SM-2 обоснован его широким применением в образовательных приложениях (Anki, Mnemosyne, SuperMemo) и доказанной эффективностью для долговременного запоминания.

**Математическая модель SM-2.**

Алгоритм оперирует следующими параметрами для каждой карточки (пара «вопрос — ответ»):

- $EF$ (Easiness Factor) — фактор лёгкости, определяющий скорость увеличения интервалов. Начальное значение: 2.5. Минимальное допустимое: 1.3.
- $I(n)$ — интервал до следующего повторения в днях после $n$-го повторения.
- $n$ — номер текущего повторения (repetitions).
- $q$ — оценка качества ответа от 0 до 5, где:
  - 0 — полное отсутствие знания («Забыл полностью»);
  - 1 — неправильный ответ, но при показе вспомнил;
  - 2 — неправильный ответ, казалось лёгким;
  - 3 — правильный ответ с существенными затруднениями;
  - 4 — правильный ответ с небольшими затруднениями;
  - 5 — идеальный ответ без затруднений.

**Формула обновления фактора лёгкости:**

$$EF' = EF + (0.1 - (5 - q) \cdot (0.08 + (5 - q) \cdot 0.02))$$

При $q = 5$ (идеальный ответ): $EF' = EF + 0.1$ (фактор увеличивается).
При $q = 4$: $EF' = EF + 0.0$ (фактор не меняется).
При $q = 3$: $EF' = EF - 0.14$ (фактор уменьшается).
При $q < 3$: фактор существенно снижается, интервал сбрасывается.

Если $EF' < 1.3$, устанавливается $EF' = 1.3$ (минимальный порог для предотвращения слишком частых повторений).

**Формула расчёта интервала:**

$$I(n) = \begin{cases} 1, & \text{если } n = 1 \\ 6, & \text{если } n = 2 \\ I(n-1) \cdot EF, & \text{если } n > 2 \end{cases}$$

При неудачном ответе ($q < 3$) интервал сбрасывается:
- $I = 0.04$ дня (≈1 час) — агрессивный повтор для забытых карточек;
- $n$ (repetitions) обнуляется;
- $EF$ сохраняется (не сбрасывается к 2.5).

**Приоритизация карточек при загрузке.** Метод `GET /api/trainer/sm2-cards/{user_session}` возвращает карточки в следующем порядке приоритета:

1. **Просроченные** (`next_review < NOW()`): карточки, интервал повторения которых уже истёк;
2. **Новые** (`repetitions = 0`): карточки, которые пользователь ещё не изучал;
3. **Выученные** (`next_review > NOW()`): карточки, повторение которых ещё не наступило.

Такая приоритизация обеспечивает оптимальную стратегию обучения: сначала повторяем забытое, затем изучаем новое.

**Таблица `sr_cards` — хранение состояния SM-2:**

```sql
CREATE TABLE IF NOT EXISTS sr_cards (
    id SERIAL PRIMARY KEY,
    user_session VARCHAR(100) NOT NULL,
    question_id INTEGER REFERENCES questions(id) ON DELETE CASCADE,
    easiness_factor FLOAT DEFAULT 2.5,
    interval_days FLOAT DEFAULT 0,
    repetitions INTEGER DEFAULT 0,
    next_review TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    last_quality INTEGER DEFAULT 0,
    total_reviews INTEGER DEFAULT 0,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(user_session, question_id)
);
```

Ограничение `UNIQUE(user_session, question_id)` гарантирует, что для каждой пары «пользователь — вопрос» существует ровно одна карточка SM-2.

*FR-3.2. Mock-собеседования.*

Система должна генерировать наборы вопросов для имитации реального собеседования. Параметры:
- Тема (опционально);
- Уровень сложности (опционально);
- Количество вопросов (5–50);
- Случайная выборка из одобренных вопросов по заданным фильтрам.

По завершении рассчитываются:
- Процент правильных ответов ($\frac{correct}{total} \times 100\%$);
- Время прохождения в секундах;
- Детализированные результаты по каждому вопросу (JSON-массив `answers`).

Результаты сохраняются в таблице `mock_interviews` и доступны по эндпоинту `GET /api/mock-interview/history/{user_session}`.

*FR-3.3. Детальная карточка вопроса.*

**FR-4. Аналитические инструменты.**

*FR-4.1. Навыки из вакансий HeadHunter.*

Система должна хранить и отображать данные о навыках, востребованных в вакансиях на HH.ru. Для каждого навыка хранится:

```sql
CREATE TABLE IF NOT EXISTS hh_skills (
    id SERIAL PRIMARY KEY,
    profession VARCHAR(200) NOT NULL,
    skill VARCHAR(200) NOT NULL,
    vacancy_count INTEGER DEFAULT 0,
    total_vacancies INTEGER DEFAULT 0,
    percentage FLOAT DEFAULT 0.0,
    source VARCHAR(50) DEFAULT 'hh.ru',
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(profession, skill)
);
```

Процент встречаемости навыка рассчитывается как:

$$P_{skill} = \frac{V_{skill}}{V_{total}} \times 100\%$$

где $V_{skill}$ — количество вакансий, требующих данный навык; $V_{total}$ — общее количество проанализированных вакансий для данной профессии.

Данные группируются по профессиям. Поддерживается пагинация на стороне клиента. Всего в системе хранится 214 навыков по 26 профессиям.

**FR-5. Пользовательский контент (UGC).**

*FR-5.1. Пользовательские ответы с голосованием.*

Пользователи (идентифицируемые по `user_session`) могут добавлять собственные ответы на вопросы. Ограничения:

**FR-7. Мониторинг и отслеживание прогресса.**

*FR-7.1. WebSocket-уведомления.*

Во время обработки видео клиент получает обновления прогресса в реальном времени по WebSocket-соединению `ws://host/ws/{clientId}`. Формат сообщений:

```json
{
    "type": "progress",
    "task_id": "uuid-string",
    "progress": 65,
    "status": "extracting",
    "step": "Извлечение вопросов через LLM..."
}
```

Типы сообщений:
- `progress` — обновление прогресса (0–100%);
- `completed` — задача завершена (содержит количество извлечённых вопросов);
- `error` — ошибка обработки (содержит текст ошибки);
- `pong` — ответ на keepalive.

*FR-7.2. Логирование этапов pipeline.*

Каждый этап обработки фиксируется в журнале задачи:

| Этап | Прогресс | Статус | Описание |
|------|----------|--------|----------|
| Создание задачи | 0% | pending | «Задача создана» |
| Начало скачивания | 5% | downloading | «Начинаем скачивание видео...» |
| Скачивание завершено | 20% | downloaded | «Скачано: {title} ({duration}с)» |
| Начало транскрибации | 25% | transcribing | «Транскрибация аудио через Whisper...» |
| Транскрибация завершена | 60% | transcribed | «{segments} сегментов, {chars} символов» |
| Извлечение вопросов | 65% | extracting | «Извлечение вопросов через LLM...» |
| Вопросы извлечены | 85% | extracted | «Извлечено {count} вопросов» |
| Сохранение в БД | 90% | saving | «Сохранение в базу данных...» |
| Готово | 100% | completed | «Готово!» |

Журнал ограничен 50 последними записями для предотвращения неограниченного роста.

**NFR-2. Масштабируемость.**

*NFR-2.1. Горизонтальное масштабирование транскрибации.*

Архитектура `WhisperOrchestrator` реализует паттерн «оркестратор — воркеры» с возможностью масштабирования до $N$ воркеров. Принцип: один воркер обрабатывает одно полное аудио (per-task scaling). Это исключает:
- Проблемы с разделением аудио на фрагменты (потеря контекста на границах);
- Необходимость синхронизации между фрагментами;
- Перекрытие сегментов и дублирование текста.

Текущий лимит: `MAX_WHISPER_WORKERS = 2` (ограничено RAM).

*NFR-2.2. Масштабируемость данных.*

Модель данных нормализована для поддержки роста до 100 000 вопросов:
- Индексы обеспечивают O(log N) поиск по B-tree;
- FAISS обеспечивает O(N) поиск (brute-force), что достаточно до ~50 000 вопросов. При превышении — переход на `IndexIVFFlat` с O(√N) поиском.

**NFR-3. Отказоустойчивость.**

*NFR-3.1. Multi-provider LLM.*

При недоступности одного LLM-провайдера система автоматически переключается на альтернативный:

```
OpenRouter (Llama-3.1-70B) → Gemini (2.0-flash → 1.5-flash) → Groq (Llama-3.1-70B)
```

Для Groq реализован exponential backoff при rate limiting:
- Максимум 5 попыток;
- Начальная задержка: 10 секунд;
- Множитель: 2× (10с → 20с → 40с → 80с → 160с).

*NFR-3.2. Персистентная модель Whisper.*

Модель faster-whisper (~3 ГБ) загружается при старте контейнера и остаётся resident в памяти. Кэш модели хранится в именованном Docker-томе `whisper_cache`, что исключает повторное скачивание при перезапуске контейнера.

*NFR-3.3. Ожидание воркера.*

При отсутствии свободных Whisper-воркеров система ожидает до 1 часа (720 итераций × 5 секунд) без потери задачи:

```python
for i in range(720):
    await asyncio.sleep(5)
    worker = await self.get_available_worker()
    if worker:
        break
```

*NFR-3.4. Healthcheck-и контейнеров.*

| Backend | — (depends_on healthy) | — | — | — | — |

### 3.1.4. Роли пользователей и пользовательские сценарии

В системе выделены две основные роли с различными уровнями доступа.

**Роль 1: Пользователь (User).**

Анонимный пользователь, идентифицируемый по UUID сессии в `localStorage`:

```javascript
function getUserSession() {
    let session = localStorage.getItem('user_session')
    if (!session) {
        session = 'user_' + Date.now() + '_' + Math.random().toString(36).substr(2, 9)
        localStorage.setItem('user_session', session)
    }
    return session
}
```

UUID генерируется при первом визите и сохраняется на стороне клиента. Формат: `user_1703000000000_a1b2c3d4e`. Преимущества:
- Не требует регистрации (снижает барьер входа);
- Не собирает персональные данные (GDPR-совместимость);
- Сохраняется между сеансами в одном браузере.

**Пользовательские сценарии:**

## 3.2. Архитектура системы

### 3.2.1. Обоснование архитектурного стиля

Для реализации системы выбрана **сервис-ориентированная архитектура (SOA)** с элементами **микросервисной архитектуры**, реализованная через Docker Compose.

**Причины выбора SOA с контейнеризацией:**

1. **Гетерогенность технологий.** Система объединяет компоненты на различных стеках:
   - Python 3.11 — backend (FastAPI, ML-библиотеки);
   - JavaScript (Node.js 18) — frontend (Vue 3, Vite 5);
   - C++ — движок транскрибации (CTranslate2, faster-whisper);
   - PostgreSQL — СУБД;
   - Redis — кэш и очередь задач.

   Каждый компонент работает в изолированном контейнере со своими зависимостями, что исключает конфликты версий и упрощает обновление отдельных компонентов.

2. **Различные профили ресурсов.** Сервис транскрибации (Whisper) потребляет 3–8 ГБ RAM при активной обработке, тогда как backend потребляет 200–500 МБ. Контейнеризация позволяет:
   - Настраивать ресурсные ограничения через `deploy.resources.limits`;
   - Задавать memory reservation для Whisper: 4 ГБ гарантированных, до 8 ГБ лимит;
   - Мониторить потребление ресурсов каждого контейнера независимо.

3. **Независимый жизненный цикл.** Модель транскрибации может быть обновлена (large-v3 → large-v3-turbo) без пересборки backend-а. Frontend может быть пересобран без перезагрузки Whisper-модели (~3 ГБ в памяти, ~2 минуты холодного старта).

4. **Горизонтальное масштабирование.** WhisperOrchestrator реализует паттерн «оркестратор — воркеры». Каждый воркер обрабатывает полное аудио целиком. В production-среде количество воркеров масштабируется через Docker Compose `--scale` или Kubernetes Deployment.

**Анализ альтернативных архитектурных подходов:**

| Подход | Преимущества | Недостатки | Вердикт |
|--------|-------------|------------|---------|
| Монолит | Простота разработки, лёгкий deployment | Whisper ~3 ГБ при каждом перезапуске; невозможность масштабирования транскрибации отдельно | Отклонён |
| Полный микросервис (RabbitMQ/Kafka) | Надёжная очередь сообщений, независимые deployments | Избыточная сложность для MVP; оверхед на брокер сообщений | Отклонён |
| Serverless (Lambda) | Auto-scaling, pay-per-use | Persistent модель невозможна; лимит 15 мин на функцию | Отклонён |
| SOA + Docker Compose | Баланс простоты и разделения; быстрый старт; подходит для MVP | Ручное масштабирование; нет автоматического service discovery | **Выбрано** |

**Паттерны проектирования, применённые в архитектуре:**

1. **Object Pool** — управление пулом Whisper-воркеров в `WhisperOrchestrator`;
2. **Pipeline** — последовательная обработка видео (download → transcribe → extract → save);
3. **Observer (WebSocket)** — уведомление клиентов о прогрессе обработки;
4. **Strategy** — выбор LLM-провайдера через переменную окружения;
5. **Facade** — централизованный API-клиент (`api/client.js`) для frontend.

Backend ожидает готовности PostgreSQL и Redis через `depends_on.condition: service_healthy`. Whisper Worker запускается параллельно с backend и имеет `start_period: 180s` (3 минуты) для загрузки модели ~3 ГБ.

**Auto-migration при старте.**

Backend при старте выполняет идемпотентную миграцию через `CREATE TABLE IF NOT EXISTS` в функции `lifespan()`:

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    # Startup
    conn = await asyncpg.connect(DATABASE_URL)
    try:
        await conn.execute("""
            CREATE TABLE IF NOT EXISTS video_suggestions (...);
            CREATE TABLE IF NOT EXISTS feedback (...);
            CREATE TABLE IF NOT EXISTS bookmarks (...);
            -- ... ещё 17 таблиц
        """)
        # Наполнение профессий
        await conn.execute("""
            INSERT INTO professions (...) VALUES (...)
            ON CONFLICT (slug) DO NOTHING
        """)
    finally:
        await conn.close()
    
    # Инициализация компонентов
    video_downloader = VideoDownloader(TEMP_DIR)
    whisper_orchestrator = WhisperOrchestrator(max_workers=MAX_WHISPER_WORKERS)
    await whisper_orchestrator.initialize()
    await initialize_similarity_search()
    
    yield  # Приложение работает
    
    # Shutdown
    await redis_client.close()
```

Этот подход обеспечивает:
- Идемпотентность: повторный запуск безопасен (IF NOT EXISTS);
- Автоматическое создание всех таблиц без ручных миграций;
- Наполнение справочных данных (профессии) с защитой от дубликатов (`ON CONFLICT DO NOTHING`).

## 3.3. Проектирование структуры данных

### 3.3.1. Модель предметной области

Предметная область системы подготовки к IT-собеседованиям включает следующие ключевые сущности:

**Центральные сущности:**

1. **Вопрос (Question)** — центральная сущность. Текст вопроса с собеседования, характеризуемый темой, сложностью, вероятностью, автоматически сгенерированным ответом. Связан со многими видеозаписями (M:N).

2. **Видеозапись (ProcessedVideo)** — обработанная видеозапись. URL, заголовок, платформа. Из одной видеозаписи извлекается множество вопросов (1:N → M:N через `question_video`).

3. **Профессия (Profession)** — IT-специализация. Slug, название, иконка, CSS-цвет. Связана с темами (1:N через `profession_topics`), которые в свою очередь являются атрибутом вопросов (foreign key-like через совпадение строк `topic`).

**Пользовательские сущности:**

4. **SM-2 Карточка (SRCard)** — прогресс пользователя по конкретному вопросу. Содержит EF, interval, repetitions, next_review. Привязана к user_session + question_id (UNIQUE).

5. **Пользовательский ответ (UserAnswer)** — UGC-ответ на вопрос. Поддерживает голосование через отдельную таблицу `answer_votes`.

6. **Закладка (Bookmark)** — сохранённый вопрос с опциональной заметкой.

**Аналитические сущности:**

7. **HH Навык (HHSkill)** — навык из вакансий HH.ru с процентом встречаемости по профессии.

8. **Тестовое задание (TestAssignment)** — задание от IT-компании с описанием, требуемыми навыками и ссылкой.

**Триггеры.** Триггер `update_updated_at_column()` автоматически обновляет поле `updated_at` при модификации записей:

```sql
CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = CURRENT_TIMESTAMP;
    RETURN NEW;
END;
$$ language 'plpgsql';

CREATE TRIGGER tr_questions_updated
    BEFORE UPDATE ON questions
    FOR EACH ROW EXECUTE FUNCTION update_updated_at_column();
```

### 3.4.1. Принципы UX/UI-проектирования

При проектировании интерфейса применены 5 принципов:

1. **Dark-first дизайн.** Тёмная схема на основе собственной дизайн-системы (CSS Custom Properties, основной фон `#0c0c0f`, поверхность `#16161a`, акцент `#7c5cfc`). Целевая аудитория — разработчики, привыкшие к тёмным IDE. Радиальные градиенты для глубины интерфейса.

2. **Контент-ориентированность.** NavBar + Footer, без боковых панелей. Максимум пространства для контента.

3. **Прогрессивное раскрытие (Progressive Disclosure).** Три уровня информации:
   - Уровень 1: список профессий (карточки с количеством вопросов);
   - Уровень 2: список вопросов профессии (таблица с фильтрами);
   - Уровень 3: детальная карточка вопроса (ответ, видео, UGC).

4. **Консистентность через дизайн-систему.** Все UI-элементы реализованы через утилитарные CSS-классы в `global.css` (.btn, .btn-primary, .btn-ghost, .btn-danger, .btn-sm, .btn-lg, .badge, .card, .input, .spinner, .progress), обеспечивающие единый стиль без зависимости от сторонних UI-библиотек.

5. **Адаптивность.** CSS Grid с `auto-fill` и `minmax()` для автоматической подгонки колонок.

### 3.4.5. Production-конфигурация Nginx

В production-конфигурации фронтенд собирается в статические файлы (`npm run build`) и раздаётся через nginx:

```nginx
server {
    listen 80;
    root /usr/share/nginx/html;

    # Gzip-сжатие
    gzip on;
    gzip_vary on;
    gzip_min_length 1024;
    gzip_types text/plain text/css application/javascript application/json;

    # Безопасность
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-XSS-Protection "1; mode=block" always;

    # Кэширование статики (1 год, immutable)
    location ~* \.(js|css|png|jpg|svg|woff2)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # SPA fallback (Vue Router history mode)
    location / {
        try_files $uri $uri/ /index.html;
    }

    # Reverse proxy к backend
    location /api {
        proxy_pass http://backend:8000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_read_timeout 300s;
    }
}
```
