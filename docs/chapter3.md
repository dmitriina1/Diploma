# Глава 3. ПРОЕКТИРОВАНИЕ ИНФОРМАЦИОННОЙ СИСТЕМЫ

## 3.1. Требования к информационной системе

### 3.1.1. Функциональные требования

Проектирование информационной системы для автоматизированной подготовки к IT-собеседованиям начинается с формализации функциональных требований. На основе анализа предметной области (глава 2) и исследования конкурентных решений были выявлены ключевые функциональные блоки, формирующие архитектуру системы.

**FR-1. Обработка видеоматериалов с собеседованиями.**

Система должна обеспечивать полный автоматизированный pipeline извлечения данных из видеозаписей технических собеседований. Данное требование декомпозируется на следующие подтребования:

- FR-1.1. Мультиплатформенная загрузка видео. Система должна поддерживать загрузку видеоконтента с не менее чем 6 популярных видеоплатформ: YouTube, VK Video, Rutube, OK.ru, Dailymotion и Vimeo. Выбор платформ обоснован анализом предметной области: русскоязычный контент с IT-собеседованиями распределён преимущественно между YouTube (≈60%), VK Video (≈20%) и Rutube (≈15%).

- FR-1.2. Автоматическая транскрибация речи. Система должна преобразовывать аудиодорожку видеозаписи в текст на русском языке с использованием нейронной модели распознавания речи. Качество транскрибации должно обеспечивать WER (Word Error Rate) не более 15% для русской речи в условиях чистого аудио.

- FR-1.3. Извлечение вопросов и ответов через LLM. Из полученного транскрипта система должна автоматически выделять вопросы интервьюера и соответствующие ответы кандидата с помощью больших языковых моделей (LLM). Система должна поддерживать выбор из нескольких LLM-провайдеров для обеспечения отказоустойчивости.

- FR-1.4. Извлечение таймкодов. Для каждого извлечённого вопроса система должна определять временную метку (таймкод) его появления в видео, обеспечивая навигацию к конкретному моменту видеозаписи.

- FR-1.5. Семантическая дедупликация вопросов. При сохранении новых вопросов система должна выполнять проверку на семантические дубликаты с использованием векторных представлений (embeddings) и не допускать повторного добавления содержательно идентичных вопросов.

- FR-1.6. Загрузка локальных видеофайлов. Помимо URL-адресов, администратор должен иметь возможность загрузить видеофайл напрямую с локального устройства для обработки.

**FR-2. Каталогизация и навигация по вопросам.**

- FR-2.1. Профессиональная классификация. Система должна предоставлять каталог IT-профессий (не менее 25) с привязанными к ним технологиями (темами). Каждая профессия должна агрегировать вопросы по соответствующим технологиям.

- FR-2.2. Многоуровневая фильтрация. Вопросы должны поддерживать фильтрацию по профессии, технологии (topic), уровню сложности (junior / middle / senior), а также полнотекстовый и семантический поиск.

- FR-2.3. Расчёт вероятности вопроса. На основе статистики встречаемости вопроса в обработанных видеозаписях система должна рассчитывать вероятность его появления на реальном собеседовании по формуле:

$$P(q) = \frac{V_q}{V_{total}} \times 100\%$$

где $V_q$ — количество видео, в которых встречается вопрос $q$; $V_{total}$ — общее количество обработанных видеозаписей.

- FR-2.4. Семантический поиск похожих вопросов. Для любого вопроса система должна находить семантически схожие вопросы с использованием FAISS-индекса на основе косинусного сходства эмбеддингов.

**FR-3. Обучающие инструменты.**

- FR-3.1. Тренажёр с интервальным повторением (SM-2). Система должна реализовывать алгоритм SuperMemo 2 для адаптивного планирования повторений. Алгоритм SM-2 определяет следующие параметры карточки:

$$EF' = EF + (0.1 - (5 - q) \cdot (0.08 + (5 - q) \cdot 0.02))$$

где $EF$ — фактор лёгкости (easiness factor, начальное значение 2.5, минимум 1.3); $q$ — оценка качества ответа (0–5).

Интервал повторения вычисляется по формуле:

$$I(n) = \begin{cases} 1, & \text{если } n = 1 \\ 6, & \text{если } n = 2 \\ I(n-1) \cdot EF, & \text{если } n > 2 \end{cases}$$

При неудачном ответе ($q < 3$) интервал сбрасывается до 1 часа ($I = 0.04$ дня), а счётчик повторений обнуляется.

- FR-3.2. Mock-собеседования. Система должна генерировать наборы вопросов для имитации реального собеседования с учётом выбранной темы и уровня сложности. По завершении рассчитывается процент правильных ответов и время прохождения.

- FR-3.3. Детальная карточка вопроса. Для каждого вопроса должна быть доступна основная информация, автоматически сгенерированный ответ, список видео-источников с таймкодами, семантически похожие вопросы и пользовательские ответы.

**FR-4. Аналитические инструменты.**

- FR-4.1. Навыки из вакансий HeadHunter. Система должна хранить и отображать данные о навыках, востребованных в вакансиях на HH.ru, с указанием процента вакансий, требующих каждый навык. Навыки должны быть сгруппированы по профессиям с поддержкой пагинации.

- FR-4.2. Тестовые задания от компаний. Система должна предоставлять каталог тестовых заданий, выдаваемых IT-компаниями, с фильтрацией по профессии и уровню сложности.

- FR-4.3. Публичная статистика. На главной странице должна отображаться общая статистика: количество вопросов, обработанных видео, топ технологий, распределение по уровням сложности.

**FR-5. Пользовательский контент (UGC).**

- FR-5.1. Пользовательские ответы с голосованием. Пользователи должны иметь возможность добавлять собственные ответы на вопросы (до 3 на один вопрос). Другие пользователи могут голосовать за или против ответа.

- FR-5.2. Закладки и заметки. Пользователи должны сохранять вопросы в закладки и оставлять личные заметки к вопросам.

- FR-5.3. Предложение видео. Пользователи должны иметь возможность предложить видео для обработки через форму на сайте. Предложения проходят модерацию администратором.

- FR-5.4. Обратная связь. Система должна поддерживать различные типы обратной связи: лайки, дизлайки, жалобы, предложения, оценки качества ответов.

**FR-6. Административная панель.**

- FR-6.1. Модерация вопросов. Администратор должен просматривать все извлечённые вопросы, одобрять или отклонять их, редактировать текст, тему и сложность.

- FR-6.2. Автоматическая генерация ответов. Администратор должен запускать генерацию ответов через LLM для отдельных вопросов или пакетно (bulk-генерация).

- FR-6.3. Объединение дубликатов. Администратор должен объединять семантически одинаковые вопросы, при этом все связи с видео переносятся на целевой вопрос, а вероятности пересчитываются.

- FR-6.4. Управление видео. Администратор должен просматривать обработанные видео с количеством извлечённых вопросов, редактировать заголовки и удалять видео.

- FR-6.5. Мониторинг задач. Администратор должен видеть все задачи обработки с детализированным логом этапов, статусами и прогрессом в реальном времени (через WebSocket).

- FR-6.6. Экспорт данных. Администратор должен экспортировать вопросы в форматах JSON и CSV.

**FR-7. Мониторинг и отслеживание прогресса.**

- FR-7.1. WebSocket-уведомления. Во время обработки видео клиент должен получать обновления прогресса в реальном времени без необходимости опроса (polling).

- FR-7.2. Логирование этапов pipeline. Каждый этап обработки (скачивание, транскрибация, извлечение, сохранение) должен фиксироваться в журнале задачи с таймштампом и процентом выполнения.


### 3.1.2. Нефункциональные требования

**NFR-1. Производительность.**

- NFR-1.1. Время обработки видео длительностью 60 минут не должно превышать 30 минут на CPU-конфигурации (AMD Ryzen 7, 32 ГБ RAM).

- NFR-1.2. Время ответа API для CRUD-операций (чтение, создание, обновление, удаление) не должно превышать 200 мс при нагрузке до 50 одновременных пользователей.

- NFR-1.3. Семантический поиск похожих вопросов на базе из 10 000 вопросов должен выполняться не более чем за 100 мс.

- NFR-1.4. WebSocket-обновления должны доставляться клиенту с задержкой не более 500 мс от момента обновления статуса.

**NFR-2. Масштабируемость.**

- NFR-2.1. Архитектура сервиса транскрибации должна поддерживать горизонтальное масштабирование. Оркестратор должен управлять пулом до $N$ Whisper-воркеров, распределяя задачи по принципу «один воркер — одно полное аудио» без разбиения аудио на фрагменты.

- NFR-2.2. Модель данных должна быть нормализована для поддержки роста до 100 000 вопросов без деградации производительности запросов за счёт индексации.

**NFR-3. Отказоустойчивость.**

- NFR-3.1. При недоступности одного LLM-провайдера система должна автоматически переключиться на альтернативный. Поддерживается не менее 3 провайдеров.

- NFR-3.2. Whisper-модель должна загружаться в память при старте контейнера и оставаться resident в течение всего жизненного цикла сервиса, исключая повторную загрузку ~3 ГБ модели.

- NFR-3.3. Очередь задач должна обеспечивать ожидание свободного воркера до 1 часа без потери задачи.

**NFR-4. Удобство использования (Usability).**

- NFR-4.1. Интерфейс должен быть адаптивным и корректно отображаться на экранах с разрешением от 320px (мобильные устройства).

- NFR-4.2. Тёмная цветовая тема оформления для снижения зрительной нагрузки при длительной работе.

- NFR-4.3. Время загрузки главной страницы — не более 3 с при стабильном соединении.

**NFR-5. Безопасность.**

- NFR-5.1. API-ключи LLM-провайдеров должны передаваться исключительно через переменные окружения и не отображаться в логах.

- NFR-5.2. Пользовательская сессия идентифицируется анонимно через уникальный UUID, хранимый в localStorage, без сбора персональных данных.

- NFR-5.3. Все внешние HTTP-запросы к LLM-провайдерам должны выполняться с таймаутом не более 180 с для предотвращения зависаний.

**NFR-6. Развёртываемость (Deployability).**

- NFR-6.1. Система должна разворачиваться командой `docker-compose up -d` без ручной установки зависимостей.

- NFR-6.2. Все миграции базы данных должны выполняться автоматически при старте backend-сервиса (auto-migration в lifespan).

- NFR-6.3. Модель Whisper должна кэшироваться в именованном Docker-томе, исключая повторное скачивание при перезапуске контейнера.

**NFR-7. Поддерживаемость (Maintainability).**

- NFR-7.1. Backend реализуется как единый модульный файл с чётким разделением на секции (конфигурация, модели, pipeline, API-эндпоинты, вспомогательные функции), что упрощает навигацию и сопровождение.

- NFR-7.2. Документация API генерируется автоматически через OpenAPI/Swagger, доступная по URL `/docs`.

## 3.2. Архитектура системы

### 3.2.1. Обоснование архитектурного стиля

Для реализации системы выбрана **сервис-ориентированная архитектура (SOA)** с элементами **микросервисной архитектуры**, реализованная через Docker Compose. Данный выбор обоснован следующими факторами:

1. **Гетерогенность технологий.** Система объединяет компоненты на различных технологических стеках: Python-backend (FastAPI), JavaScript-frontend (Vue.js), C++-движок транскрибации (CTranslate2/faster-whisper). Каждый компонент работает в изолированном контейнере с собственными зависимостями.

2. **Различные профили ресурсов.** Сервис транскрибации требует 3+ ГБ RAM для загрузки модели Whisper и интенсивных вычислений CPU/GPU, тогда как backend-сервис потребляет 200–500 МБ RAM. Контейнеризация позволяет настраивать ресурсные ограничения индивидуально.

3. **Независимый жизненный цикл.** Модель транскрибации может быть обновлена (например, с large-v3 на large-v3-turbo) без пересборки backend-а или frontend-а. Аналогично, frontend может быть пересобран без перезагрузки контейнера с Whisper-моделью.

4. **Горизонтальное масштабирование.** Архитектура WhisperOrchestrator реализует паттерн «оркестратор — воркеры», позволяющий масштабировать количество Whisper-воркеров в зависимости от нагрузки. Каждый воркер обрабатывает полное аудио целиком (per-task scaling), что исключает проблемы с разделением аудио на фрагменты.

**Альтернативы и причины отказа от них:**

- *Монолитная архитектура* — не подходит из-за невозможности раздельного масштабирования вычислительно-интенсивного сервиса транскрибации. Загрузка модели Whisper (~3 ГБ) при каждом перезапуске монолита неприемлема.

- *Полноценная микросервисная архитектура с брокером сообщений (RabbitMQ/Kafka)* — избыточна для текущей стадии проекта (MVP). Координация через REST API и Redis достаточна при нагрузке до 10 одновременных задач.

- *Serverless (AWS Lambda / Cloud Functions)* — не подходит из-за необходимости persistent-модели в памяти (Whisper) и ограничений на время выполнения функции (транскрибация может занимать до 30 минут).


### 3.2.2. Компонентная архитектура

Система состоит из 6 контейнеризованных сервисов, взаимодействующих через выделенную bridge-сеть Docker.

```
┌────────────────────────────────────────────────────────────────────────┐
│                       Docker Compose Cluster                          │
│                                                                        │
│  ┌───────────────┐  ┌───────────────┐  ┌────────────┐  ┌────────────┐ │
│  │ Frontend NEW  │  │ Frontend OLD  │  │  Backend   │  │  Whisper   │ │
│  │ Vue 3.4 +     │  │ Vue 3 +       │  │  FastAPI   │  │  Worker    │ │
│  │ Custom CSS    │  │ PrimeVue      │  │ (67 endp.) │  │ large-v3-  │ │
│  │ :3000         │  │ :3001         │  │ :8000      │  │ turbo      │ │
│  └───────┬───────┘  └───────┬───────┘  └─────┬──────┘  │ :8001      │ │
│          │                  │                │         └─────┬──────┘ │
│          └──────────────────┼────────────────▶│◀─────────────┘        │
│                             └────────────────▶│                       │
│                                         ┌─────┴──────┐               │
│                                         │            │               │
│                                   ┌─────▼────┐ ┌─────▼──────┐       │
│                                   │PostgreSQL│ │   Redis    │       │
│                                   │15-alpine │ │  7-alpine  │       │
│                                   │ :5432    │ │  :6379     │       │
│                                   │(20 табл.)│ │(кэш,задачи)│       │
│                                   └──────────┘ └────────────┘       │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

**Компонент 1: Frontend NEW (порт 3000).**

Основное одностраничное приложение (SPA) на Vue 3.4 с собственной дизайн-системой на CSS Custom Properties (без сторонних UI-библиотек). Включает 12 представлений (views) и 2 переиспользуемых компонента (NavBar, AppFooter). Все UI-элементы реализованы через утилитарные CSS-классы (.btn, .badge, .card, .input, .spinner, .progress) в едином файле `global.css`. Тёмная тема с фиолетовыми акцентами (#7c5cfc). Сборка через Vite 5, state management через Pinia, HTTP-клиент — Axios. В production-конфигурации приложение собирается в статические файлы и раздаётся через nginx.

**Компонент 1a: Frontend OLD (порт 3001).**

Легаси-версия фронтенда на Vue 3 с библиотекой компонентов PrimeVue (тема lara-dark-purple). Сохранена для сравнительного анализа и A/B-тестирования с новым интерфейсом. Оба фронтенда подключены к одному и тому же Backend.

**Компонент 2: Backend (порт 8000).**

Центральный сервис на FastAPI, реализующий 55 REST API-эндпоинтов и 1 WebSocket-эндпоинт. Организован как единый модульный файл (`main_new.py`, 3237 строк) с чётким разделением на секции:
- Конфигурация и глобальные объекты;
- WhisperOrchestrator (оркестратор воркеров);
- Core Processing Pipeline (основной pipeline обработки);
- API-эндпоинты (Public, Admin, Export);
- Вспомогательные функции (фильтрация, дедупликация, LLM-вызовы).

Backend использует асинхронные клиенты: `asyncpg` для PostgreSQL, `redis.asyncio` для Redis, `httpx` для HTTP-запросов к LLM-провайдерам и Whisper-сервису.

**Компонент 3: Whisper Worker (порт 8001).**

Специализированный микросервис для транскрибации речи. Использует библиотеку `faster-whisper`, обеспечивающую 4–6-кратное ускорение по сравнению с оригинальным OpenAI Whisper за счёт движка CTranslate2 (оптимизированный C++ inference). Модель загружается в память один раз при старте контейнера и остаётся resident. Предоставляет 3 эндпоинта:
- `GET /health` — проверка готовности;
- `POST /transcribe` — транскрибация загруженного файла;
- `POST /transcribe-path` — транскрибация файла по пути в общем томе.

Конфигурируется через переменные окружения: `WHISPER_MODEL` (large-v3-turbo по умолчанию), `DEVICE` (cpu/cuda/auto), `COMPUTE_TYPE` (int8/float16/auto), `CPU_THREADS`, `BEAM_SIZE`, `VAD_ENABLED`.

**Компонент 4: PostgreSQL 15 (порт 5432).**

Реляционная СУБД с расширением `pg_trgm` для триграммного поиска. Хранит 20 таблиц, сгруппированных в 3 логических слоя:
- Ядро (core): `questions`, `processed_videos`, `question_video`, `processing_tasks`;
- Пользовательские функции (v2): `video_suggestions`, `feedback`, `bookmarks`, `question_tags`, `mock_interviews`, `uploaded_videos`, `question_views`, `user_notes`;
- Расширенная аналитика (v3): `professions`, `profession_topics`, `sr_cards`, `user_answers`, `answer_votes`, `test_assignments`, `hh_skills`, `question_timecodes`.

**Компонент 5: Redis 7 (порт 6379).**

In-memory хранилище, используемое для:
- Кэширование состояния задач обработки (TTL 24 часа);
- Очередь задач (list-структура `global:tasks`);
- Mapping WebSocket-клиентов к задачам;
- Кэширование FAISS-индекса и эмбеддингов (сериализация через `pickle`);
- Хранение транскрипций задач.

**Взаимодействие компонентов.** Все сервисы объединены в Docker bridge-сеть `app-network`. Backend обращается к Whisper Worker по внутреннему DNS-имени (`whisper-worker:8001`). Временные файлы (аудио, субтитры) передаются через общий Docker-том `temp-data`, монтируемый в `/app/temp` обоих контейнеров (backend и whisper-worker).


### 3.2.3. Архитектура развёртывания

Система разворачивается через единый файл `docker-compose.yml`, определяющий 6 сервисов (Frontend NEW, Frontend OLD, Backend, Whisper Worker, PostgreSQL, Redis), 4 именованных тома и 1 bridge-сеть.

**Именованные тома (Named Volumes):**

| Том | Контейнер(ы) | Назначение |
|-----|-------------|------------|
| `postgres-data` | postgres | Персистентные данные PostgreSQL |
| `redis-data` | redis | Дамп Redis (AOF/RDB) |
| `whisper-cache` | whisper-worker | Кэш загруженной модели Whisper (~3 ГБ) |
| `temp-data` | backend, whisper-worker | Общий том для временных аудиофайлов |

**Конфигурация GPU.** Предусмотрены три варианта docker-compose файлов:
- `docker-compose.yml` — базовая конфигурация (CPU);
- `docker-compose.cpu.yml` — оптимизированная CPU-конфигурация с `int8` квантизацией;
- `docker-compose.gpu.yml` — GPU-конфигурация с NVIDIA runtime и `float16` вычислениями.

**Порядок запуска.** Docker Compose обеспечивает корректный порядок запуска через `depends_on`:

```
PostgreSQL → Redis → Backend → Whisper Worker
                  → Frontend
```

Backend при старте выполняет auto-migration: создаёт все 20 таблиц через `CREATE TABLE IF NOT EXISTS` в функции `lifespan()`, что обеспечивает идемпотентность запуска.


## 3.3. Проектирование структуры данных

### 3.3.1. Модель предметной области

Предметная область системы подготовки к IT-собеседованиям включает следующие ключевые сущности и их взаимосвязи:

**Вопрос (Question)** — центральная сущность системы. Представляет собой вопрос, задаваемый на техническом собеседовании. Характеризуется текстом, темой (технологией), уровнем сложности, вероятностью появления на собеседовании и автоматически сгенерированным ответом. Один вопрос может встречаться в нескольких видеозаписях.

**Видеозапись (ProcessedVideo)** — обработанная системой видеозапись собеседования. Характеризуется URL-адресом, заголовком, платформой и датой обработки. Из одной видеозаписи извлекается множество вопросов.

**Профессия (Profession)** — IT-специализация, объединяющая набор технологий (topics). Используется для навигации и фильтрации вопросов. Связана с вопросами через промежуточную сущность «Тема профессии» (ProfessionTopic).

**SM-2 Карточка (SRCard)** — состояние прогресса конкретного пользователя по конкретному вопросу в системе интервального повторения. Содержит фактор лёгкости, интервал, количество повторений и дату следующего повторения.

**Пользовательский ответ (UserAnswer)** — ответ, написанный пользователем на вопрос из каталога. Поддерживает голосование (votes).

**HH Навык (HHSkill)** — навык, востребованный на рынке труда, с указанием профессии и процента вакансий, требующих данный навык.

### 3.3.3. Схема базы данных

Физическая модель базы данных реализована в PostgreSQL 15 с расширением `pg_trgm`. Ниже описаны ключевые таблицы и стратегия индексирования.

**Таблица `questions` — основная таблица вопросов.**

| Поле | Тип | Ограничения | Описание |
|------|-----|-------------|----------|
| id | SERIAL | PRIMARY KEY | Идентификатор |
| question | TEXT | NOT NULL | Текст вопроса |
| answer | TEXT | — | Текст ответа (LLM) |
| topic | VARCHAR(100) | INDEX | Технология/тема |
| difficulty | VARCHAR(20) | CHECK (junior/middle/senior) | Уровень сложности |
| probability | FLOAT | DEFAULT 0.0 | Вероятность (%) |
| timecode | VARCHAR(20) | — | Таймкод в видео |
| approved | BOOLEAN | DEFAULT FALSE, INDEX | Одобрен ли |
| source_url | VARCHAR(500) | — | URL источника |
| video_title | VARCHAR(500) | — | Заголовок видео |
| created_at | TIMESTAMP | DEFAULT NOW() | Дата создания |
| updated_at | TIMESTAMP | TRIGGER | Дата обновления |

**Таблица `sr_cards` — карточки интервального повторения SM-2.**

| Поле | Тип | Ограничения | Описание |
|------|-----|-------------|----------|
| id | SERIAL | PRIMARY KEY | Идентификатор |
| user_session | VARCHAR(100) | NOT NULL, UNIQUE(user_session, question_id) | Сессия пользователя |
| question_id | INTEGER | REFERENCES questions(id) CASCADE | Ссылка на вопрос |
| easiness_factor | FLOAT | DEFAULT 2.5 | EF по SM-2 |
| interval_days | FLOAT | DEFAULT 0 | Интервал (дни) |
| repetitions | INTEGER | DEFAULT 0 | Счётчик повторений |
| next_review | TIMESTAMP | DEFAULT NOW() | Дата следующего повторения |
| last_quality | INTEGER | DEFAULT 0 | Последняя оценка (0–5) |
| total_reviews | INTEGER | DEFAULT 0 | Всего повторений |

**Стратегия индексирования.** В базе данных определены 22 индекса для оптимизации наиболее частых запросов:

- B-tree индексы на полях `topic`, `difficulty`, `approved` таблицы `questions` — для фильтрации каталога;
- B-tree индексы на `question_id` и `video_id` таблицы `question_video` — для вычисления вероятности;
- B-tree индексы на `user_session` таблиц `bookmarks`, `mock_interviews`, `user_notes` — для извлечения данных пользователя;
- B-tree индексы на `status` таблиц `processing_tasks`, `video_suggestions` — для фильтрации задач.

**Триггеры.** Определены триггеры `update_updated_at_column()` для автоматического обновления поля `updated_at` при модификации записей в таблицах `questions`, `processing_tasks`, `video_suggestions` и `user_notes`.

**Обеспечение ссылочной целостности.** Используются ON DELETE CASCADE для зависимых таблиц (`sr_cards`, `bookmarks`, `question_tags`, `question_views`, `user_notes`, `question_video`, `question_timecodes`, `user_answers`, `answer_votes`) и ON DELETE SET NULL для `feedback.question_id`, сохраняя обратную связь даже при удалении вопроса.


## 3.4. Проектирование пользовательского интерфейса

### 3.4.1. Принципы UX/UI-проектирования

При проектировании интерфейса системы были приняты следующие принципы:

1. **Dark-first дизайн.** Тёмная цветовая схема на основе собственной дизайн-системы с CSS Custom Properties (основной фон `#0c0c0f`, поверхность `#16161a`, фиолетовый акцент `#7c5cfc`) выбрана как основная, поскольку целевая аудитория (разработчики) привыкла к тёмным средам (VS Code, терминалы, IDE). Тёмный фон снижает зрительную нагрузку при длительной работе с текстом.

2. **Контент-ориентированность.** Минималистичная навигация (NavBar + Footer), максимум экранного пространства отведено контенту. Боковые панели и сложные меню отсутствуют.

3. **Прогрессивное раскрытие (Progressive Disclosure).** Информация отображается поуровнево: список профессий → список вопросов → детальная карточка вопроса. Дополнительные данные (видео, похожие вопросы, UGC-ответы) загружаются по требованию.

4. **Консистентность через дизайн-систему.** Все UI-элементы реализованы через единый файл `global.css` с утилитарными CSS-классами (.btn, .btn-sm, .btn-lg, .badge, .card, .input, .spinner, .progress), обеспечивающими визуальную и поведенческую согласованность без зависимости от сторонних UI-библиотек.

5. **Адаптивность.** Сетка макета адаптируется к экранам от 320px до 2560px. Профессии отображаются в grid-layout с автоматической подгонкой количества колонок.

### 3.4.3. Взаимодействие интерфейса с бизнес-логикой

Клиентское приложение взаимодействует с backend через централизованный API-клиент (`api/client.js`), который инкапсулирует HTTP-запросы с помощью Axios. Все запросы направляются на базовый URL `http://localhost:8000`.

**State Management.** Глобальное состояние приложения управляется через Pinia store, хранящий:
- UUID сессии пользователя (генерируется при первом визите и сохраняется в `localStorage`);
- Текущий режим навигации;
- Кэшированные данные профессий.

**WebSocket-интеграция.** Для мониторинга обработки видео frontend устанавливает WebSocket-соединение по адресу `ws://localhost:8000/ws/{clientId}`. Сообщения прогресса имеют структуру:

```json
{
  "type": "progress",
  "task_id": "uuid",
  "progress": 65,
  "status": "extracting",
  "step": "Извлечение вопросов через LLM..."
}
```

**Компонентная модель.** 2 переиспользуемых компонента обеспечивают каркас интерфейса, остальная логика инкапсулирована в представлениях (views):

| Компонент | Назначение |
|-----------|------------|
| NavBar | Навигационная панель с маршрутами, аватаром и адаптивным меню |
| AppFooter | Нижний колонтитул с копирайтом |

Модальные окна, формы обратной связи, диалоги подтверждения и прочие UI-элементы реализованы через Vue 3 Teleport и scoped CSS непосредственно в views, что обеспечивает самодостаточность каждого представления.

**Дизайн-система.** Все UI-элементы построены на CSS Custom Properties (без PrimeVue), определённых в `global.css`:
- Кнопки: `.btn`, `.btn-primary`, `.btn-ghost`, `.btn-danger`, `.btn-sm`, `.btn-lg`
- Поля ввода: `.input`, `.input:focus` с фиолетовой подсветкой
- Карточки: `.card` с `backdrop-filter: blur(12px)` и полупрозрачным фоном
- Бейджи: `.badge`, `.badge-green`, `.badge-yellow`, `.badge-red`, `.badge-purple`
- Прогресс-бары: `.progress`, `.progress-bar` с CSS-переменной `--p` для ширины
- Спиннер: `.spinner` (CSS-анимация `spin`)
