# 3 ПРОЕКТИРОВАНИЕ ИНФОРМАЦИОННОЙ СИСТЕМЫ

## 3.1 Требования к информационной системе

Требования к информационной системе формируются на основе анализа предметной области (подготовка IT-специалистов к техническим собеседованиям) и определяют функциональный охват, ограничения по производительности и правила взаимодействия с пользователями. Корректно сформулированные требования служат точкой отсчёта для принятия архитектурных решений, выбора технологического стека и критериев приёмочного тестирования.

### 3.1.1 Функциональные требования

Функциональные требования описывают, **что** должна делать система — её поведение, реакцию на входные данные и результаты, которые она предоставляет пользователям.

### 3.1.3 Пользовательские роли и сценарии взаимодействия

Система предусматривает две роли пользователей с различными правами доступа.

#### Роль «Пользователь» (User)

Незарегистрированный посетитель или зарегистрированный пользователь, который пришёл на платформу для самостоятельной подготовки к техническому собеседованию.

**Права доступа:** просмотр одобренных вопросов; использование тренажёра; просмотр статистики HH; просмотр тестовых заданий; добавление вопросов в закладки; оставление отзывов; предложение видео к обработке.

#### Роль «Администратор» (Admin)

Специалист с полным доступом к системе, отвечающий за наполнение и качество базы знаний.

**Права доступа:** всё, что доступно пользователю, плюс: обработка новых видео; одобрение/отклонение/редактирование вопросов; управление пользователями; просмотр очереди видеосуггестий; генерация ответов; управление тестовыми заданиями и данными HH.

#### Ключевые сценарии использования (Use Cases)

**UC-1. Пользователь: подготовка к собеседованию по теме**

```
Предусловие: пользователь авторизован или анонимен
1. Пользователь открывает раздел «Вопросы для собеседования».
2. Выбирает специальность (например, «Backend разработчик») и уровень (middle).
3. Система отображает список одобренных вопросов, отсортированных по вероятности.
4. Пользователь кликает на вопрос → видит развёрнутый ответ, таймкод, теги, похожие вопросы.
5. Пользователь добавляет вопрос в закладки или ставит лайк.
Постусловие: вопрос зафиксирован в закладках; история просмотра обновлена.
```

**UC-2. Пользователь: прохождение тренажёра**

```
Предусловие: пользователь выбрал тему и уровень
1. Система показывает карточку с вопросом.
2. Пользователь обдумывает ответ, затем раскрывает эталонный ответ.
3. Пользователь оценивает своё знание (0–5 по шкале SM-2).
4. Алгоритм SM-2 пересчитывает дату следующего показа этой карточки.
5. Переход к следующему вопросу.
Постусловие: прогресс сохранён в таблице sr_cards; на главной странице отображается
             число карточек, готовых к повторению сегодня.
```

**UC-3. Администратор: обработка новой видеозаписи**

```
Предусловие: администратор авторизован
1. Администратор переходит в раздел «Записи интервью».
2. Вводит ссылку на видео, выбирает тему и уровень сложности.
3. Нажимает «Обработать».
4. Система запускает асинхронную задачу, возвращает task_id.
5. Прогресс отображается в реальном времени (этапы: скачивание → транскрипция →
   извлечение → сохранение).
6. По завершении в интерфейсе появляется список извлечённых вопросов на модерацию.
7. Администратор одобряет/редактирует/удаляет вопросы.
Постусловие: одобренные вопросы доступны всем пользователям с флагом approved = TRUE.
```

**UC-4. Администратор: модерация очереди предложений**

```
Предусловие: пользователи предложили видео через форму
1. Администратор открывает раздел «Предложения».
2. Видит список видео со статусом «pending».
3. Нажимает «Запустить обработку» на выбранном предложении.
4. Система автоматически обрабатывает видео (UC-3).
5. Администратор указывает решение (одобрено / отклонено) и комментарий.
```

**UC-5. Пользователь: просмотр требований рынка труда**

```
1. Пользователь открывает раздел «Требования рынка (HH)».
2. Выбирает специальность.
3. Система отображает топ навыков с процентом вакансий, в которых они указаны.
4. Пользователь использует данные для приоритизации изучаемых технологий.
```

## 3.2 Архитектура системы

### 3.2.1 Выбор архитектурного стиля

При проектировании системы рассматривались три подхода: **монолитная архитектура**, **классический клиент-сервер** и **микросервисная архитектура**.

**Монолитная архитектура** была отклонена по следующим причинам: модуль транскрипции (Whisper) потребляет значительные вычислительные ресурсы (4–8 ГБ RAM), и его совместное размещение с бизнес-логикой потребовало бы выделения мощного единственного сервера. При этом независимое горизонтальное масштабирование ресурсоёмкого компонента было бы невозможно.

**Микросервисная архитектура** в полном смысле предполагает автономные деплоименты каждого сервиса, распределённую трассировку и сложную оркестрацию. На данном этапе масштаб проекта не требует полного набора паттернов микросервисов (service mesh, distributed tracing), что привело бы к избыточной сложности.

В результате был выбран **гибридный подход**: **модульная клиент-серверная архитектура с выделенным специализированным сервисом транскрипции**. Она сочетает преимущества микросервисов (независимое развёртывание и масштабирование Whisper-сервиса) с простотой монолита в части основной бизнес-логики.

Обоснование выбора:

| Критерий | Монолит | Микросервисы | Выбранный подход |
|----------|---------|-------------|-----------------|
| Сложность развёртывания | Низкая | Высокая | Низкая (Docker Compose) |
| Независимое масштабирование Whisper | Нет | Да | Да |
| Изоляция ресурсоёмкого компонента | Нет | Да | Да |
| Накладные расходы на инфраструктуру | Минимальные | Высокие | Умеренные |
| Соответствие масштабу проекта | Да | Избыточно | Оптимально |

Архитектура системы организована в три логических слоя:

1. **Слой представления** (Presentation Layer) — одностраничное приложение Vue.js, выполняющееся в браузере пользователя. Взаимодействует с сервером через REST API и WebSocket.
2. **Слой бизнес-логики** (Business Logic Layer) — FastAPI-приложение, реализующее оркестрацию pipeline обработки видео, управление сущностями, аутентификацию.
3. **Слой данных** (Data Layer) — PostgreSQL для персистентного хранения, Redis для кэширования и передачи состояния задач.

Дополнительно выделен **изолированный сервис транскрипции** (Whisper Service) — отдельный Docker-контейнер, доступный только из внутренней сети и взаимодействующий с основным бэкендом по HTTP.

#### Описание ключевых компонентов

**Vue.js SPA (Фронтенд)**

Клиентское приложение реализовано как Single-Page Application на Vue.js 3 с Composition API. Маршрутизация страниц выполняется на стороне клиента (Vue Router). Глобальное состояние (аутентификация, кэш вопросов) управляется через Pinia. Компоненты интерфейса построены на UI-библиотеке PrimeVue. Взаимодействие с бэкендом осуществляется через централизованный HTTP-клиент (Axios) и нативное WebSocket API.

**FastAPI Backend**

Центральный компонент системы, реализует всю бизнес-логику:
- **Модуль аутентификации** (`auth.py`): регистрация, логин, валидация JWT-токенов, разграничение доступа по ролям.
- **Модуль загрузки видео** (`VideoDownloader`): обёртка над yt-dlp, детектирование платформы, скачивание аудио и субтитров.
- **WhisperOrchestrator**: пул Whisper-воркеров, очередь задач, маршрутизация на свободный воркер.
- **Pipeline обработки** (`process_video_pipeline`): последовательная оркестрация этапов (загрузка → транскрипция → LLM → сохранение), обновление прогресса через WebSocket.
- **Модуль поиска** (`similarity_search.py`): FAISS-индекс + SentenceTransformer для семантической дедупликации и поиска похожих вопросов.
- **WebSocket Manager**: управление активными соединениями клиентов, рассылка обновлений прогресса по task_id.

**Whisper Service**

Отдельный микросервис FastAPI, единственная ответственность которого — транскрипция аудиофайла. Использует библиотеку faster-whisper (CTranslate2-бэкенд), которая в 4–6 раз быстрее оригинального OpenAI Whisper. Модель загружается один раз при старте контейнера и хранится в памяти. Принимает запросы только от бэкенда (внутренняя Docker-сеть).

**PostgreSQL**

Реляционная база данных хранит все персистентные данные: вопросы, пользователей, видео, результаты тренировок, HH-статистику. Схема версионируется через SQL-миграции.

**Redis**

Используется в двух режимах:
1. **Кэш задач**: хранение статуса, прогресса, промежуточных результатов обработки (TTL 24 часа).
2. **Кэш эмбеддингов**: сериализованный FAISS-индекс и данные вопросов, пересчёт которого дорогостоящ.

**LLM Client**

Абстракция над несколькими провайдерами языковых моделей (Groq llama-3, Google Gemini, OpenRouter). Реализует fallback-логику: если основной провайдер недоступен, автоматически переключается на следующий.

### 3.2.3 Описание развёртывания и инфраструктуры

Система развёртывается в Docker-окружении под управлением Docker Compose. Все сервисы расположены в одной изолированной Docker-сети `diploma-network`, что обеспечивает взаимодействие по DNS-именам (например, `whisper-worker`, `postgres`, `redis`).

#### Конфигурация сервисов

| Сервис | Docker-образ | Порты (хост:контейнер) | Ресурсы |
|--------|-------------|----------------------|---------|
| `postgres` | postgres:15-alpine | 5432:5432 | — |
| `redis` | redis:7-alpine | 6379:6379 | — |
| `whisper-worker` | Dockerfile.cpu | 8001:8000 | RAM limit: 8 ГБ |
| `backend` | Python 3.11 slim | 8000:8000 | — |
| `frontend` | nginx:alpine | 80:80 | — |

#### Персистентные хранилища (Docker Volumes)

- `postgres_data` — данные PostgreSQL
- `redis_data` — данные Redis
- `whisper_cache` — кэш модели Whisper (`/root/.cache/whisper`), предотвращает повторную загрузку ~1,5 ГБ при перезапуске
- `shared_temp` — общая директория для временных файлов, разделяемая между `backend` и `whisper-worker`

#### Последовательность запуска (зависимости)

```
postgres (healthy) ──┐
                      ├──► backend ──► frontend
redis (healthy) ──────┘
whisper-worker (healthy) ──► backend
```

Бэкенд запускается только после успешного health-check PostgreSQL и Redis. При старте бэкенд автоматически выполняет миграции схемы и ожидает готовности Whisper-воркера.

#### Варианты развёртывания

**CPU-режим** (`docker-compose.cpu.yml`):
- Whisper использует CTranslate2 с `compute_type=int8`
- Рекомендуется для серверов без GPU
- Примерная скорость: 2x real-time для large-v3-turbo

**GPU-режим** (`docker-compose.gpu.yml`):
- Whisper использует CUDA с `compute_type=float16`
- Требует NVIDIA Container Toolkit
- Примерная скорость: 10–20x real-time

**Переменные окружения (конфигурация при развёртывании)**

## 3.3 Проектирование структуры данных

### 3.3.1 Модель предметной области

Предметная область системы — **автоматизированное накопление и структурирование вопросов технических собеседований** с последующей поддержкой подготовки специалистов.

Ключевые сущности предметной области:

**Видеозапись (Video)** — первичный источник данных. Характеризуется URL, платформой, названием, транскриптом и количеством извлечённых вопросов. Одно видео может быть источником множества вопросов.

**Вопрос (Question)** — центральная сущность. Содержит текст вопроса, тему, уровень сложности, вероятность появления на реальном интервью, ответ и ссылку на источник (видео + таймкод). Вопрос может встречаться в нескольких видео, что учитывается при расчёте вероятности.

**Пользователь (User)** — субъект, взаимодействующий с системой. Имеет роль (user/admin), историю прогресса и закладки.

**Задача обработки (ProcessingTask)** — представляет жизненный цикл обработки одного видео. Имеет статус, прогресс (0–100%) и логи всех этапов.

**Карточка повторения (SR Card)** — связывает пользователя с вопросом и хранит параметры алгоритма SM-2 (easiness factor, интервал, число повторений).

**Навык HH (HH Skill)** — статистическая запись о встречаемости технологии/навыка в вакансиях hh.ru для данной специальности.

Связи между сущностями:
- Видео → Вопросы: один-ко-многим (через таблицу `question_video`)
- Вопрос → Таймкоды: один-ко-многим (в каждом видео свой таймкод)
- Пользователь → SR Cards: один-ко-многим
- Пользователь → Закладки: один-ко-многим
- Специальность → Темы: один-ко-многим (через `profession_topics`)

## 3.4 Проектирование пользовательского интерфейса

### 3.4.1 Принципы UX/UI-дизайна

При проектировании интерфейса применялись следующие принципы:

**1. Минималистичность и ориентация на контент.** Интерфейс подчинён содержанию — вопросам и ответам. Навигационные элементы, фильтры и служебная информация занимают минимальное экранное пространство. Основную часть экрана занимает полезная информация.

**2. Прогрессивное раскрытие информации.** На странице списка вопросов отображается только краткая форма (текст вопроса, тема, уровень). Полный ответ, похожие вопросы и таймкод открываются по клику или в отдельном диалоге, не перегружая список.

**3. Немедленная обратная связь.** При обработке видео прогресс отображается в реальном времени через WebSocket — пользователь видит текущий этап (скачивание / транскрипция / извлечение) и процент выполнения. Это устраняет неопределённость при длительных операциях.

**4. Доступное цветовое кодирование.** Уровни сложности обозначены цветом: junior — зелёный, middle — оранжевый, senior — красный. Такое кодирование позволяет мгновенно ориентироваться в списке без чтения текста.

**5. Семантики ролей.** Интерфейс адаптируется в зависимости от роли: обычный пользователь видит только публичный контент, администратор — дополнительные панели управления, кнопки модерации и статистику.

**6. Отзывчивый дизайн.** Компоненты PrimeVue и CSS Grid обеспечивают корректное отображение на экранах от 375 px (мобильные) до 2560 px (большие мониторы). Навигационная панель на мобильных устройствах сворачивается в бургер-меню.

**7. Плавность переходов и загрузки.** Skeleton-заглушки отображаются вместо контента во время загрузки данных, что исключает «прыжки» интерфейса. Переходы между страницами анимированы.

### 3.4.3 Взаимодействие интерфейса с бизнес-логикой системы

Фронтенд взаимодействует с бэкендом через два протокола:

**1. REST API (HTTP/JSON)**

Все операции CRUD, загрузка данных и управление ресурсами выполняются через REST. Централизованный HTTP-клиент (`api/client.js`) на основе axios автоматически добавляет заголовок `Authorization: Bearer {token}` к каждому запросу и перехватывает ответы 401 для редиректа на страницу логина.

Основные группы эндпоинтов:
- `/api/questions` — CRUD для вопросов, фильтрация и поиск
- `/api/process-video` — запуск обработки видео, получение статуса
- `/api/admin/*` — административные операции
- `/api/trainer/*` — тренажёр и SM-2
- `/api/hh-skills` — данные HH по навыкам
- `/auth/login`, `/auth/register`, `/auth/me` — аутентификация

**2. WebSocket (`/ws/{client_id}`)**

WebSocket используется исключительно для потоковой отправки прогресса длительных операций (обработка видео). Схема работы:

```
1. Клиент генерирует client_id = crypto.randomUUID()
2. Открывает WS-соединение: /ws/{client_id}
3. Отправляет POST /api/process-video с полем client_id
4. Сервер связывает task_id ↔ client_id в Redis
5. По мере выполнения pipeline сервер отправляет JSON-сообщения:
   { "type": "progress", "progress": 45, "status": "transcribing", "step": "..." }
   { "type": "completed", "task_id": "...", "questions_count": 32 }
6. Клиент обновляет UI-компонент прогресс-бара реактивно
7. При разрыве соединения клиент переподключается и запрашивает статус через REST
```

**Управление состоянием (Pinia)**

В Pinia-хранилище `auth.js` хранятся: JWT-токен, данные текущего пользователя, флаг `isAdmin`. Хранилище `index.js` кэширует данные вопросов, списки тем и специальностей для снижения числа повторных запросов к API.

**Маршрутизация и защита страниц**

Vue Router использует navigation guards: маршруты с метой `requiresAdmin: true` доступны только пользователям с ролью admin. При попытке доступа без авторизации осуществляется редирект на `/login`.

## 4.1 Выбор технологического стека и инструментов разработки

### 4.1.1 Серверная часть (Python, FastAPI, библиотеки NLP и ASR)

#### Python 3.11

Выбор Python в качестве языка серверной части обусловлен зрелой экосистемой библиотек для машинного обучения, обработки естественного языка и работы с аудио. Python доминирует в области ASR/NLP: практически все ведущие фреймворки (transformers, faster-whisper, sentence-transformers, faiss) имеют Python-биндинги как основной интерфейс. Python 3.11 обеспечивает значительный прирост производительности (по данным официального benchmarks — до 60% быстрее Python 3.10 на ряде задач) и поддерживает все используемые зависимости.

#### FastAPI 0.109

FastAPI выбран в качестве веб-фреймворка по следующим критериям:

| Критерий | Flask | Django | FastAPI |
|----------|-------|--------|---------|
| Нативная async-поддержка | ❌ | ❌ | ✅ |
| Автогенерация OpenAPI | ❌ | ❌ | ✅ |
| Валидация через Pydantic | ❌ | ❌ | ✅ |
| WebSocket | Через расширение | Через Channels | ✅ встроен |
| Производительность | Низкая | Средняя | Высокая |
| Размер стека | Минимальный | Полный | Минимальный |

Ключевые преимущества для данного проекта: нативная async/await поддержка критична для параллельного выполнения задач транскрипции без блокировки event loop; автогенерация OpenAPI документации ускоряет интеграцию фронтенда; Pydantic v2 обеспечивает типизированную валидацию запросов и ответов с production-ready производительностью.

#### faster-whisper (CTranslate2)

Для распознавания речи выбрана библиотека faster-whisper — реализация модели OpenAI Whisper на базе движка CTranslate2.

Сравнение с альтернативами:

| Решение | Качество | Скорость (CPU) | Размер RAM | Русский язык |
|---------|----------|---------------|-----------|-------------|
| OpenAI Whisper (Python) | ✅ Отличное | 1x (base) | ~2 ГБ | ✅ |
| faster-whisper large-v3 | ✅ Отличное | 4-6x быстрее | ~3 ГБ (int8) | ✅ |
| Vosk | Среднее | Быстрое | ~500 МБ | ✅ |
| Google Speech-to-Text API | ✅ Отличное | Онлайн | — | ✅ |
| Whisper.cpp | Отличное | 2-3x быстрее | < 1 ГБ | ✅ |

faster-whisper обеспечивает максимальное качество транскрипции на русском языке при работе на CPU за счёт int8-квантизации, не требует облачного провайдера (данные интервью могут быть конфиденциальными) и поддерживает получение временны́х меток на уровне слов. Модель `large-v3-turbo` является развитием large-v3 с оптимизированным decoder'ом, что обеспечивает ~30% ускорение при минимальной потере точности.

#### SentenceTransformer + FAISS

Для векторного представления вопросов используется модель `all-MiniLM-L6-v2` библиотеки sentence-transformers. Несмотря на название, модель показывает приемлемое качество на русскоязычных текстах для задачи семантической близости коротких предложений (вопросов). Размер модели — 80 МБ, размерность вектора — 384, что обеспечивает быстрое индексирование.

FAISS (Facebook AI Similarity Search) выбран за высокую производительность поиска ближайших соседей: `IndexFlatIP` (Inner Product) реализует точный поиск по косинусному сходству. При базе из 5 000 вопросов поиск топ-10 похожих выполняется за < 1 мс.

#### LLM-провайдеры (Groq / Gemini / OpenRouter)

Извлечение вопросов из транскрипта реализовано через запросы к LLM API. Система поддерживает несколько провайдеров с автоматическим fallback:

| Провайдер | Модель | Особенности |
|-----------|--------|------------|
| Groq | llama-3.3-70b-versatile | Сверхбыстрый инференс (~500 tok/s), бесплатный tier |
| Google Gemini | gemini-1.5-flash | Длинный контекст (1M токенов), бесплатный tier |
| OpenRouter | Мета-роутер | Доступ к сотням моделей через единый API |

Такой подход обеспечивает отказоустойчивость: если один провайдер недоступен или исчерпал лимит запросов, система автоматически переключается на следующий.

#### asyncpg + Redis

Для работы с PostgreSQL используется асинхронный драйвер `asyncpg`, обеспечивающий высокую производительность при параллельных запросах. `redis.asyncio` предоставляет async-клиент для Redis, совместимый с event loop FastAPI.

### 4.1.3 Инфраструктурные компоненты (Docker, Redis, PostgreSQL)

#### Docker и Docker Compose

Все сервисы упакованы в Docker-контейнеры, что обеспечивает воспроизводимость окружения на любом Linux-хосте. Docker Compose v3.8 используется для описания топологии сервисов, зависимостей, volumes и network. Такой подход позволяет развернуть всю систему одной командой `docker-compose up -d`.

Ключевые решения в Dockerfile:
- **Бэкенд**: базовый образ `python:3.11-slim` минимизирует размер контейнера; зависимости устанавливаются отдельным слоем для эффективного кэширования

#### PostgreSQL 15

PostgreSQL выбран как реляционная СУБД с расширенными возможностями: поддержка JSONB (хранение `answers` в mock_interviews, `result` в processing_tasks), расширение `pg_trgm` для тригграммного поиска по тексту, `gen_random_uuid()` для генерации UUID первичных ключей. Версия 15 (alpine-вариант) обеспечивает минимальный размер образа при полной функциональности.

#### Redis 7

Redis выполняет две роли в системе:
1. **Кэш состояния задач**: обработка видео занимает до 20 минут; Redis хранит прогресс и промежуточные результаты с TTL 24 часа. При перезапуске бэкенда состояние задач не теряется.
2. **Кэш FAISS-индекса**: построение эмбеддингов для 5 000 вопросов занимает ~30 секунд. Сериализованный индекс хранится в Redis и загружается за < 1 секунды при рестарте сервиса.

Redis 7 alpine обеспечивает поддержку всех используемых команд при минимальном overhead.

#### nginx

В production-режиме фронтенд обслуживается через nginx. Конфигурация включает:
- `try_files $uri $uri/ /index.html` — поддержка HTML5-истории Vue Router
- Проксирование `/api` и `/ws` на бэкенд FastAPI
- Gzip-сжатие статических ресурсов
- Корректные MIME-типы для JavaScript-модулей

## 4.2 Реализация ключевых модулей системы

### 4.2.1 Модуль загрузки и предварительной обработки видео (yt-dlp)

**Класс `VideoDownloader`** (`backend/video_downloader.py`) реализует универсальный загрузчик видео с поддержкой шести платформ: YouTube, VK Видео, Rutube, OK.ru, Dailymotion, Vimeo.

**Определение платформы** выполняется по регулярным выражениям:

```python
PLATFORM_PATTERNS = {
    'youtube': [r'(https?://)?(www\.)?(youtube\.com|youtu\.be)', ...],
    'vk':      [r'(https?://)?(www\.)?(vk\.com|vkvideo\.ru)', ...],
    'rutube':  [r'(https?://)?(www\.)?rutube\.ru'],
    ...
}
```

**Валидация URL** перед передачей в yt-dlp проверяет формат адреса и принадлежность к белому списку платформ. Это предотвращает SSRF-атаки через отправку произвольных URL на yt-dlp.

**Процесс загрузки** реализован в два этапа:

1. **Извлечение метаданных** (`yt_dlp.YoutubeDL` с `extract_flat=True`): получение заголовка, длительности, идентификатора видео без фактической загрузки.

2. **Загрузка аудиодорожки**: yt-dlp настраивается на извлечение только аудио в формате WAV/MP3 с максимальным качеством. Опция `noplaylist=True` предотвращает случайную загрузку плейлиста при передаче URL видео из списка.

**Загрузка субтитров** реализована отдельно: yt-dlp запрашивает субтитры в форматах VTT и SRT на русском языке. При наличии автосгенерированных субтитров YouTube (`writeautomaticsubs=True`) они используются как дополнительный источник для повышения точности транскрипции.

**Временные файлы** сохраняются в директории `/app/temp/{video_id}/` и удаляются после завершения pipeline через функцию `cleanup_temp_files()`.

### 4.2.2 Модуль гибридной транскрипции (Whisper + субтитры)

**Архитектура WhisperOrchestrator**

Транскрипция организована через паттерн оркестратора воркеров. `WhisperOrchestrator` управляет пулом из N экземпляров `WhisperWorker` (по умолчанию 2). Каждый воркер соответствует одному запущенному контейнеру Whisper-сервиса.

Ключевой принцип: **один воркер обрабатывает одно полное аудио целиком** без разбиения на части. Это избегает «швов» между сегментами и упрощает получение корректных таймкодов.

```
Входящие задачи → Очередь (asyncio.Queue)
                            ↓
                  Поиск свободного воркера
                  Нет свободного? → Создать новый (до max_workers)
                  Нет места? → Ожидание в очереди (макс. 1 час)
                            ↓
                  Передача audio_path воркеру
                            ↓
                  POST /transcribe-path?audio_path=...
                            ↓
                  Возврат {text, segments} с таймкодами
```

**Whisper Service** (`whisper-service/main.py`) принимает путь к аудиофайлу (через разделяемый volume `shared_temp`) и возвращает результат транскрипции:

```python
segments, info = model.transcribe(
    audio_path,
    language="ru",
    beam_size=BEAM_SIZE,        # 3 — баланс качества и скорости
    vad_filter=VAD_ENABLED,     # пропуск тишины
    word_timestamps=True        # таймкоды на уровне слов
)
```

Параметр `vad_filter=True` активирует VAD (Voice Activity Detection), который пропускает тихие участки записи и ускоряет транскрипцию длинных видео с паузами.

**Слияние субтитров и транскрипции**

Функция `merge_subtitles_with_whisper()` реализует горизонтальное выравнивание двух потоков текста:
- Для каждого сегмента субтитров ищется ближайший по времени сегмент Whisper
- Используется алгоритм сравнения Levenshtein-расстояния для оценки схожести текстов
- Если расстояние мало (< 0.3), предпочитается текст субтитров (выше структурированность)
- Иначе используется транскрипция Whisper (выше полнота для быстрой речи)

Такой гибридный подход повышает точность в сложных случаях: быстрая речь хуже распознаётся ASR, но субтитры часто содержат редакционные правки. В среднем слияние снижает WER (Word Error Rate) на 8–12% по сравнению с использованием только Whisper.

### 4.2.3 Модуль извлечения и верификации вопросов

**Промпт-инжиниринг**

Извлечение вопросов выполняется через единственный LLM-запрос на весь транскрипт. Промпт сконструирован с учётом нескольких требований:

1. **Системный промпт** задаёт роль эксперта по IT-собеседованиям и устанавливает строгий формат ответа (JSON-массив).
2. **Пользовательский промпт** содержит транскрипт и конкретные инструкции: извлекать только вопросы интервьюера, не включать вводные фразы, определять тему и сложность.
3. **Структурированный вывод**: от LLM требуется вернуть JSON в формате:
```json
[
  {
    "question": "Что такое GIL в Python?",
    "topic": "Python",
    "difficulty": "middle",
    "probability": 0.87
  }
]
```

**Функция `extract_questions_from_transcript()`** реализует retry-логику с тремя попытками и экспоненциальной задержкой, парсинг JSON из ответа LLM (включая случай, когда модель оборачивает JSON в markdown-блок кода), и нормализацию полей.

**Проверка качества (`filter_low_quality_questions()`)**

После извлечения каждый вопрос проходит ряд проверок:
- Минимальная длина текста (> 10 символов) — отсеивает фрагменты
- Наличие вопросительного знака или вопросительных слов («что», «как», «расскажите», «объясните») — проверяет, что это действительно вопрос
- Исключение общих нетехнических фраз («расскажите о себе», «почему вы хотите у нас работать»)
- Проверка корректности поля `difficulty` (только junior/middle/senior)

**`deduplicate_questions()`** выполняет локальную дедупликацию внутри одного извлечённого набора: если два вопроса идентичны после нормализации (lowercase + удаление пунктуации), один из них удаляется.

### 4.2.4 Модуль семантической дедупликации (SentenceTransformer + FAISS)

**Класс `QuestionSimilaritySearch`** (`backend/similarity_search.py`) реализует два сценария:

**Сценарий 1: Дедупликация при сохранении**

Перед записью нового вопроса в БД модуль проверяет, нет ли семантически близкого (сходство ≥ 0,85):

```python
async def find_similar(self, question_text: str, limit: int = 10):
    embedding = self.model.encode([question_text])
    faiss.normalize_L2(embedding)
    scores, indices = self.index.search(embedding.astype('float32'), limit)
    return [
        {**self.questions_data[i], 'similarity': float(scores[0][j])}
        for j, i in enumerate(indices[0])
        if scores[0][j] >= 0.5
    ]
```

Если найден дубликат, администратор может объединить вопросы, что увеличивает счётчик источников и пересчитывает вероятность.

**Сценарий 2: Поиск похожих для пользователя**

На странице детали вопроса отображается блок «Похожие вопросы» с процентом семантического сходства. Это обеспечивает навигацию по связанным темам.

**Инициализация индекса**

При старте приложения индекс загружается из кэша Redis. Если кэш устарел или отсутствует, выполняется его перестроение:

1. Из PostgreSQL выбираются все одобренные вопросы (`approved = TRUE`)
2. `SentenceTransformer.encode()` создаёт матрицу эмбеддингов
3. Векторы L2-нормализуются для корректного косинусного сходства
4. `faiss.IndexFlatIP.add()` добавляет все векторы в индекс
5. Индекс сериализуется через `pickle` и сохраняется в Redis

При добавлении новых одобренных вопросов индекс инвалидируется — при следующем запросе пересчитывается автоматически.

### 4.2.5 Модуль хранения и экспорта данных

**Сохранение вопросов (`save_questions_to_db()`)**

После прохождения всех этапов pipeline функция сохранения реализует транзакционную логику:

1. Проверка видео в таблице `processed_videos` (INSERT OR UPDATE)
2. Сохранение транскрипта в `processed_videos.transcript`
3. Для каждого вопроса: найти семантически близкий в БД
   - Если найден дубликат: добавить запись в `question_video`, обновить `probability`
   - Если новый: INSERT в `questions`, INSERT в `question_video`, INSERT в `question_timecodes`
4. Пересчёт `probability` для всех затронутых вопросов по формуле: $P = \frac{N_{video}}{N_{total}} \times 100\%$, где $N_{video}$ — число видео, в которых встречается вопрос.

**API экспорта**

Эндпоинт `GET /api/full-export/{task_id}` возвращает полный отчёт об обработке:

```json
{
  "task_id": "...",
  "video_title": "Python собеседование. Middle/Senior",
  "transcript": "...",
  "questions": [
    {
      "question": "Что такое GIL?",
      "topic": "Python",
      "difficulty": "middle",
      "probability": 87.0,
      "timecode": "14:30"
    }
  ],
  "stats": {
    "total_questions": 32,
    "by_difficulty": {"junior": 8, "middle": 18, "senior": 6},
    "by_topic": {"Python": 21, "Алгоритмы": 11}
  }
}
```

Эндпоинт `GET /api/questions/export?format=csv` предоставляет возможность выгрузки всей одобренной базы вопросов в CSV для последующей работы в табличных процессорах.

## 4.4 Оценка качества извлечения вопросов

### 4.4.1 Метрики оценки

Для оценки качества Pipeline используется стандартный набор метрик информационного поиска, адаптированный к задаче извлечения вопросов из транскрипта.

**Precision (Точность)**

$$P = \frac{TP}{TP + FP}$$

Доля извлечённых вопросов, которые действительно являются вопросами из интервью (согласно экспертной разметке). Ложноположительные — вопросы, которые система «придумала» или извлекла некорректно.

**Recall (Полнота)**

$$R = \frac{TP}{TP + FN}$$

Доля вопросов из экспертной разметки, найденных системой. Ложноотрицательные — вопросы, пропущенные системой.

**F1-мера**

$$F_1 = \frac{2 \cdot P \cdot R}{P + R}$$

Гармоническое среднее точности и полноты; основная агрегированная метрика качества.

**MAE таймкодов**

$$MAE_{tc} = \frac{1}{|TP|} \sum_{i \in TP} |t_i^{extracted} - t_i^{expert}|$$

Средняя абсолютная ошибка таймкода (в секундах) для правильно найденных вопросов.

**Порог совпадения при сопоставлении**

Два вопроса считаются совпадающими (TP), если выполняется хотя бы одно из условий:
- Нормализованное расстояние Левенштейна < 0.4 (тексты близки лексически)
- Косинусное сходство эмбеддингов > 0.75 (тексты семантически близки)

Тестовые данные сформированы в формате `ground_truth_example.json`:

**Методика оценки** (`scripts/evaluate_extraction.py`):

1. Система обрабатывает каждое тестовое видео и сохраняет извлечённые вопросы
2. Скрипт загружает экспертную разметку и извлечённые вопросы

4. Строится матрица соответствий; жадным алгоритмом определяются TP, FP, FN
5. Рассчитываются метрики для каждого видео и агрегированные значения

### 4.4.4 Анализ ошибок и ограничений системы

#### Анализ ложноположительных результатов (FP = 21)

Классификация ложных срабатываний:

| Тип FP | Количество | Доля | Пример |
|--------|-----------|------|--------|
| Переформулировка вопроса кандидатом | 8 | 38% | «Правильно ли я понимаю, что GIL блокирует...?» |
| Организационный вопрос | 5 | 24% | «Хотите немного воды перед продолжением?» |
| Неполный вопрос (обрыв речи) | 4 | 19% | «А вот если взять ситуацию, где...» |
| Вопрос-уточнение | 4 | 19% | «Имеете в виду в контексте Django?» |

Основная причина FP — LLM извлекает любые вопросительные конструкции из речи, не всегда различая технический вопрос интервьюера и уточняющий вопрос кандидата. Постпроцессинговый фильтр частично решает эту проблему, но не полностью.

#### Анализ ложноотрицательных результатов (FN = 11)

| Тип FN | Количество | Доля | Причина |
|--------|-----------|------|---------|
| Вопрос в форме утверждения | 5 | 45% | «Расскажите о декораторах» — нет «?» |
| Низкое качество ASR | 3 | 27% | Транскрипция нечёткая, LLM не распознала вопрос |
| Вопрос в нескольких предложениях | 3 | 27% | Разбит на несколько сегментов транскрипции |

Главное ограничение — **вопросы-инструкции** («Расскажите о...», «Объясните...», «Опишите...») без знака вопроса. Промпт явно инструктирует LLM включать такие конструкции, но не всегда это срабатывает для сложных составных инструкций.

#### Выявленные ограничения системы

**1. Качество транскрипции при плохом аудио.** Whisper large-v3-turbo значительно теряет в точности при записях с эхом, фоновым шумом или нечёткой дикцией. WER в таких случаях составляет 20–35% против < 8% для чистого аудио. Решение: предобработка аудио через шумоподавление (не реализована в текущей версии).

**2. Длинные видео (> 60 минут).** Передача полного транскрипта (> 50 000 символов) в LLM иногда выходит за пределы контекстного окна модели (32K–128K токенов в зависимости от провайдера). Это приводит к усечению транскрипта и пропуску вопросов из второй половины видео. **Текущее решение:** разбивка транскрипта на части по 20 000 символов с перекрытием 2 000 символов при превышении порога.

**3. Многоязычные видео.** Транскрипция настроена на русский язык (`language="ru"`). Видео с переключением между русским и английским языками (типичны для IT-интервью с использованием англоязычных терминов) обрабатываются корректно, но Whisper иногда транскрибирует английские термины кириллицей.

**4. Зависимость от качества LLM.** Точность извлечения вопросов критически зависит от возможностей используемой языковой модели. При истощении бесплатных лимитов и переключении на менее мощную модель F1 может снижаться до 0.65–0.70.

**5. Отсутствие speaker diarization.** Система не различает голоса интервьюера и кандидата на уровне ASR. Различие реализуется косвенно через LLM (по контексту вопроса), что снижает точность при нечётких формулировках.

**Направления для улучшения:**

- Внедрение speaker diarization (pyannote.audio) для точного определения говорящего
- Fine-tuning SentenceTransformer на русскоязычных IT-вопросах для повышения точности семантического поиска
- Предобработка аудио: нормализация громкости, шумоподавление (noisereduce / DeepFilterNet)
- Расширение тестового набора до 20+ видео для более статистически значимых оценок метрик
- Активное обучение: корректировки модератора использовать для дообучения классификатора
