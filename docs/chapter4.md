# Глава 4. РЕАЛИЗАЦИЯ И ТЕСТИРОВАНИЕ СИСТЕМЫ

## 4.1. Технологический стек

### 4.1.1. Серверная часть

Серверная часть системы реализована на языке Python 3.11 с использованием асинхронного веб-фреймворка FastAPI. Выбор технологий обоснован требованиями к производительности, совместимости с ML-библиотеками и удобству разработки.

**FastAPI** — высокопроизводительный ASGI-фреймворк, основанный на стандарте ASGI (Asynchronous Server Gateway Interface) и библиотеке Starlette. Ключевые причины выбора:

- Встроенная поддержка `async/await` для неблокирующего ввода-вывода, критичная при одновременной обработке HTTP-запросов, WebSocket-соединений и длительных pipeline-задач (транскрибация видео до 30 минут);
- Автоматическая генерация интерактивной документации OpenAPI (Swagger UI) по адресу `/docs`, что ускоряет интеграцию frontend-клиента;
- Валидация входных данных через Pydantic-модели с автоматической генерацией ошибок 422;
- Нативная поддержка WebSocket через декоратор `@app.websocket()`.

**asyncpg** — высокопроизводительный асинхронный драйвер для PostgreSQL, написанный на Cython. Обеспечивает throughput до 100 000 запросов/с на одном ядре, что на порядок превышает производительность psycopg2. В системе используется для прямых SQL-запросов без ORM, что обеспечивает полный контроль над сгенерированным SQL и оптимальную производительность.

**redis.asyncio** — асинхронный клиент для Redis. Используется для:
- Хранения состояния задач обработки (JSON-сериализация, TTL 24 часа);
- Очереди задач (`LPUSH/LRANGE` на list-структуре `global:tasks`);
- Связи WebSocket-клиентов с задачами (`task:{id}:client`);
- Кэширования FAISS-индекса (сериализация через `pickle`).

**httpx** — HTTP-клиент с поддержкой async/await. Используется для:
- Запросов к Whisper-сервису (`POST /transcribe-path`, таймаут 7200 с для длинных видео);
- Запросов к LLM-провайдерам (OpenRouter, Google Gemini, Groq, таймаут 180 с);
- Health-check Whisper-воркеров (таймаут 5 с).

**sentence-transformers** — библиотека для создания векторных представлений текста. Используется модель `all-MiniLM-L6-v2`, генерирующая 384-мерные эмбеддинги. Модель выбрана за компактность (80 МБ) и достаточное качество для задачи семантической дедупликации на русскоязычных вопросах.

**FAISS (Facebook AI Similarity Search)** — библиотека для быстрого поиска ближайших соседей в пространстве эмбеддингов. Используется индекс `IndexFlatIP` (Inner Product) с L2-нормализованными векторами, что эквивалентно косинусному сходству. Обеспечивает поиск среди 10 000 вопросов за O(N) операций (brute-force), что достаточно для текущего масштаба данных.

**yt-dlp** — универсальный загрузчик видео, форк youtube-dl с расширенной поддержкой платформ. Обеспечивает:
- Загрузку аудиодорожки с конвертацией в MP3 (192 kbps) через FFmpeg;
- Загрузку автоматических субтитров в формате VTT;
- Поддержку 6 видеоплатформ с платформо-специфичными настройками (специальная обработка VK Video с ограничениями по размеру и длительности).

**faster-whisper** — высокопроизводительная реализация модели Whisper, использующая движок CTranslate2 для оптимизированного inference на CPU (int8 квантизация) и GPU (float16). Обеспечивает 4–6-кратное ускорение по сравнению с оригинальным OpenAI Whisper при сопоставимом качестве. Модель `large-v3-turbo` занимает ~3 ГБ в памяти и обеспечивает WER < 12% для русской речи.

**LLM-провайдеры.** Система поддерживает 3 провайдера для извлечения вопросов и генерации ответов:

| Провайдер | Модель | Назначение | Таймаут |
|-----------|--------|------------|---------|
| OpenRouter | meta-llama/llama-3.1-70b-instruct | Извлечение вопросов, генерация ответов | 180 с |
| Google Gemini | gemini-2.0-flash, gemini-1.5-flash (fallback) | Извлечение вопросов, генерация ответов | 180 с |
| Groq | llama-3.1-70b-versatile | Извлечение вопросов (с retry при rate limit) | 180 с |

Выбор провайдера осуществляется через переменную окружения `LLM_PROVIDER`. При значении `auto` система выбирает первый доступный провайдер по приоритету: OpenRouter → Gemini → Groq.


### 4.1.2. Клиентская часть

Клиентская часть реализована как одностраничное приложение (SPA) на фреймворке Vue 3.4 с использованием Composition API и синтаксиса `<script setup>`.

**Vue 3.4** — прогрессивный JavaScript-фреймворк для создания пользовательских интерфейсов. Выбран по следующим причинам:
- Реактивная система, построенная на JavaScript `Proxy`, обеспечивающая автоматическое обновление DOM при изменении данных;
- Composition API для переиспользования логики между компонентами;
- Экосистема (Vue Router 4, Pinia 2) для полноценного SPA.

**Vite 5.4** — сборщик модулей нового поколения, использующий ES modules (ESM) для мгновенного запуска dev-сервера без предварительной бандлинг-сборки. В production-режиме использует Rollup для оптимизированного бандла с tree-shaking.

**Собственная дизайн-система (global.css)** — все UI-компоненты реализованы через CSS Custom Properties и утилитарные классы без использования сторонних UI-библиотек (PrimeVue, Vuetify и т.д.). Тёмная тема с фиолетовыми акцентами (`--c-primary: #7c5cfc`), фон `#0c0c0f`, поверхность `#16161a`. Утилитарные классы: `.btn` (4 варианта), `.badge` (5 цветов), `.card`, `.input`, `.spinner`, `.progress`. Данный подход обеспечивает полный контроль над визуальным стилем и значительно сокращает размер бандла.

**Pinia 2.1.7** — официальная библиотека управления состоянием для Vue 3. Используются два хранилища: `store/index.js` (вопросы, задачи, фильтры) и `store/auth.js` (JWT-авторизация, токены).

**Axios 1.6.2** — HTTP-клиент для взаимодействия с backend API. Все запросы инкапсулированы в централизованном модуле `api/client.js`.

**@vueuse/core 10.7** — коллекция Vue Composition API утилит (useStorage, useMediaQuery, useDark и др.).

**Nginx** — веб-сервер, используемый в production-конфигурации для раздачи статических файлов и проксирования API-запросов к backend-у.

**Параллельный запуск двух фронтендов.** Система поддерживает одновременную работу двух версий интерфейса:
- Frontend NEW (порт 3000) — новый интерфейс с собственной CSS дизайн-системой (`frontend-new/`);
- Frontend OLD (порт 3001) — легаси-интерфейс на PrimeVue (`frontend-vue/`).

Оба фронтенда подключены к одному Backend (порт 8000), что позволяет проводить сравнительный анализ (A/B-тестирование) без дублирования серверной логики.


### 4.1.3. Инфраструктура

**Docker** — платформа контейнеризации. Каждый сервис описан в собственном `Dockerfile` с многоэтапной сборкой (multi-stage build):
- Backend: `python:3.11-slim` → установка зависимостей → копирование кода;
- Frontend: `node:18-alpine` → сборка Vite → `nginx:alpine` для раздачи;
- Whisper: `python:3.11-slim` → установка CTranslate2, faster-whisper, FFmpeg.

**Docker Compose** — оркестратор контейнеров. Определяет 6 сервисов (Frontend NEW, Frontend OLD, Backend, Whisper Worker, PostgreSQL, Redis), 4 именованных тома и bridge-сеть `app-network`. Три варианта конфигурации:
- `docker-compose.yml` (базовая);
- `docker-compose.cpu.yml` (CPU-оптимизация);
- `docker-compose.gpu.yml` (GPU с NVIDIA runtime).

**PostgreSQL 15 Alpine** — основная СУБД с расширением `pg_trgm` для триграммного поиска. Данные хранятся в именованном томе `postgres-data`.

**Redis 7 Alpine** — in-memory key-value хранилище. Используется как кэш задач и хранилище FAISS-индекса. Данные реплицируются через RDB-снэпшоты в именованный том `redis-data`.


## 4.2. Реализация ключевых модулей

### 4.2.1. Модуль загрузки видео (VideoDownloader)

Модуль загрузки видео реализован в файле `video_downloader.py` (352 строки) как класс `VideoDownloader` с поддержкой 6 видеоплатформ.

**Определение платформы.** Метод `detect_platform(url)` использует набор регулярных выражений для каждой платформы. Словарь `PLATFORM_PATTERNS` определяет паттерны URL для YouTube, VK Video, Rutube, OK.ru, Dailymotion и Vimeo. Алгоритм итерирует по паттернам и возвращает первое совпадение.

**Извлечение идентификатора видео.** Метод `extract_video_id(url, platform)` реализует платформо-специфичную логику:
- YouTube: извлечение 11-символьного ID из параметра `v=`, коротких URL `youtu.be/`, shorts;
- VK: извлечение составного ID формата `-123456_789012`;
- Rutube: извлечение hex-ID из пути `/video/{id}/`;
- OK.ru: извлечение числового ID из `/video/{id}`;
- Fallback: MD5-хеш URL (первые 16 символов).

**Загрузка аудио.** Метод `download_video_audio(url)` выполняет двухэтапную загрузку:

1. **Предварительный анализ** (`download=False`): получение метаданных (заголовок, длительность, thumbnail) без скачивания файла. На этом этапе проверяются ограничения для VK (макс. 60 минут).

2. **Загрузка** (`download=True`): скачивание аудиодорожки с конвертацией в MP3 (192 kbps, FFmpeg) и автоматических русских субтитров (VTT).

Для VK Video применяются специальные настройки: пониженное качество аудио для ускорения загрузки (`worst[ext=m4a]/worstaudio`), ограничение размера файла (100 МБ), отключение чанкированной загрузки, увеличенные таймауты.

**Парсинг субтитров.** Метод `_parse_vtt_subtitles(vtt_path)` реализует парсер формата WebVTT (Web Video Text Tracks). Алгоритм ищет строки с паттерном `-->` (разделитель таймкодов), затем собирает текстовые строки до следующего таймкода или пустой строки. Результат — список словарей `{start, end, text}`.


### 4.2.2. Модуль гибридной транскрибации

Транскрибация реализована через двухуровневую архитектуру: WhisperOrchestrator (backend) и Whisper-сервис (отдельный контейнер).

**WhisperOrchestrator** (классы `WhisperOrchestrator`, `WhisperWorker`, файл `main_new.py`).

Оркестратор реализует паттерн **Object Pool** для управления пулом Whisper-воркеров:

```python
class WhisperOrchestrator:
    def __init__(self, max_workers: int = 2):
        self.max_workers = max_workers
        self.workers: Dict[str, WhisperWorker] = {}
        self.task_queue: asyncio.Queue = asyncio.Queue()
```

Основной принцип — «один воркер = одно полное аудио». Аудиофайл передаётся воркеру целиком через общий Docker-том (`temp-data`), что исключает проблемы с разделением аудио на фрагменты (потеря контекста на границах, перекрытие сегментов).

Метод `get_available_worker()` реализует стратегию:
1. Поиск свободного готового воркера (is_busy=False, is_ready=True);
2. Если не найден — создание нового (до `max_workers`);
3. Если лимит достигнут — ожидание до 1 часа (720 итераций × 5 с).

**Whisper-сервис** (файл `whisper-service/main.py`, 267 строк).

Микросервис загружает модель faster-whisper в память при первом запросе и сохраняет её resident:

- Автоопределение устройства: `cuda` (при наличии NVIDIA GPU) или `cpu`;
- Автоопределение типа вычислений: `float16` для GPU, `int8` для CPU;
- VAD-фильтр (Voice Activity Detection) для пропуска участков тишины;
- Beam search с настраиваемым `beam_size` (по умолчанию 3).

**Гибридная транскрибация (слияние субтитров и Whisper).** Функция `merge_subtitles_with_whisper()` реализует алгоритм слияния платформенных субтитров с результатами Whisper. Для каждого сегмента субтитров ищется соответствующий Whisper-сегмент по временному сдвигу (< 2 секунд). Если Whisper-сегмент содержит вопросительный знак, он предпочитается субтитрам, так как Whisper лучше расставляет пунктуацию. Это критично для последующего извлечения вопросов LLM.


### 4.2.3. Модуль извлечения вопросов через LLM

Извлечение вопросов из транскрипции реализовано через функцию `extract_questions_from_transcript()` с использованием промпт-инженерии.

**Промпт-стратегия.** Формируется структурированный промпт с чёткими инструкциями:

1. Роль: «Ты — эксперт по анализу технических интервью»;
2. Задача: извлечь ВСЕ вопросы интервьюера (не кандидата);
3. Для каждого вопроса определить: тему, сложность, таймкод;
4. Формат вывода: строгий JSON-массив.

Транскрипция ограничивается первыми 50 000 символами для предотвращения превышения контекстного окна LLM (128K токенов для Llama-3.1-70B).

**Multi-provider fallback.** Функция `call_llm_api()` реализует автоматический выбор провайдера:

```
if LLM_PROVIDER == "auto":
    OpenRouter (если есть ключ) → Gemini → Groq
```

Для Gemini реализован внутренний fallback: `gemini-2.0-flash` → `gemini-1.5-flash`. Для Groq реализован exponential backoff retry при rate limiting (макс. 5 попыток, начальная задержка 10 с, множитель 2×).

**Парсинг ответа LLM.** Функция `parse_questions_from_llm()`:
1. Удаление markdown-обёрток (` ```json ... ``` `);
2. Парсинг JSON через `json.loads()`;
3. Валидация: результат должен быть списком.

**Постобработка.** Извлечённые вопросы проходят два фильтра:

1. `filter_low_quality_questions()`: удаление вопросов короче 5 символов и содержащих только междометия (regex-паттерны: `^(да|нет|ага|угу|ну|ок|м+|хм+|э)\??$`).

2. `deduplicate_questions()`: нормализация текста (удаление пунктуации, приведение к нижнему регистру, нормализация пробелов) и дедупликация по множеству (`set`).


### 4.2.4. Модуль семантического поиска (Similarity Search)

Модуль реализован в файле `similarity_search.py` (154 строки) как класс `QuestionSimilaritySearch`.

**Архитектура модуля:**

```
Текст вопроса → SentenceTransformer → 384-dim embedding → L2-normalize → FAISS IndexFlatIP
```

**Инициализация.** При запуске системы метод `initialize()`:
1. Загружает модель `all-MiniLM-L6-v2` в память (~80 МБ);
2. Проверяет наличие кэша в Redis (ключ `questions_embeddings_cache`);
3. Если кэш найден — восстанавливает FAISS-индекс и метаданные из pickle;
4. Если кэш отсутствует — строит индекс заново:
   a. Извлекает все одобренные вопросы из PostgreSQL;
   b. Генерирует эмбеддинги через `model.encode()`;
   c. Нормализует векторы через `faiss.normalize_L2()`;
   d. Добавляет в `faiss.IndexFlatIP` (Inner Product);
   e. Сохраняет в Redis через `pickle.dumps()`.

**Поиск.** Метод `find_similar(question_text, limit)`:
1. Генерирует эмбеддинг запроса через ту же модель;
2. Нормализует вектор;
3. Вызывает `index.search()` для поиска `limit + 1` ближайших соседей;
4. Исключает сам вопрос (если указан `question_id`);
5. Возвращает список с полями: `id`, `question`, `topic`, `difficulty`, `probability`, `similarity_score`.

**Инвалидация кэша.** При любом изменении вопросов (создание, обновление, удаление, одобрение, объединение) вызывается `invalidate_similarity_cache()`, очищающая ключ в Redis и сбрасывающая in-memory индекс. Перестроение индекса происходит при следующем запросе similarity search.


### 4.2.5. Модуль хранения и экспорта данных

**Сохранение вопросов** реализовано в функции `save_questions_to_db()`, выполняющей многоэтапную запись:

1. **Проверка дубликатов видео.** Запрос `SELECT id FROM processed_videos WHERE video_id = $1` предотвращает повторную обработку одного видео.

2. **Регистрация видео.** Вставка записи в `processed_videos` с указанием платформы, URL и заголовка. Возвращается `db_video_id` для последующих связей.

3. **Обработка каждого вопроса:**
   - Проверка дубликата по точному совпадению текста (case-insensitive): `SELECT id FROM questions WHERE LOWER(question) = LOWER($1)`;
   - Если дубликат найден: добавление связи `question_video` и сохранение таймкода в `question_timecodes`;
   - Если вопрос новый: вставка в `questions` (с `approved = FALSE`), создание связей `question_video` и `question_timecodes`.

4. **Пересчёт вероятностей.** Функция `update_probabilities()` выполняет массовое обновление:

```sql
UPDATE questions SET probability = (
    SELECT COALESCE(COUNT(DISTINCT qv.video_id) * 100.0 / $1, 0)
    FROM question_video qv WHERE qv.question_id = questions.id
)
```

Вероятность пересчитывается для ВСЕХ вопросов (не только одобренных), что обеспечивает актуальность данных в админ-панели.

**Экспорт данных.** Система предоставляет 3 формата экспорта:

- **JSON-экспорт задачи** (`/api/export/{task_id}`): вопросы, извлечённые в рамках одной задачи обработки видео;
- **Полный экспорт** (`/api/full-export/{task_id}`): вопросы + транскрипция + сегменты;
- **CSV-экспорт** (`/api/admin/export-csv`): все вопросы из БД с UTF-8 BOM-маркером для корректного открытия в Excel.

### 4.3.2. Тренажёр SM-2

Представление `Trainer.vue` реализует интерактивный тренажёр с алгоритмом SM-2 (SuperMemo 2). Интерфейс включает:

При загрузке компонент запрашивает `GET /api/trainer/sm2-cards/{session}` с параметрами фильтрации. Backend возвращает карточки, отсортированные по приоритету: сначала просроченные (next_review < NOW()), затем новые, затем выученные.

### 4.3.3. Детальная карточка вопроса

### 4.3.4. Административная панель

Представление `Admin.vue` реализует централизованную панель управления с tab-навигацией (собственные CSS-стили, `.tab-btn` / `.tab-btn.active`):

## 4.4. Оценка качества извлечения вопросов

### 4.4.1. Методология оценки

Для оценки качества работы pipeline извлечения вопросов из видеозаписей собеседований используется методология, основанная на сравнении с экспертной разметкой. Процесс оценки включает:

1. **Формирование тестового набора:** отбор видеозаписей различной длительности и тематики, ручная разметка вопросов экспертом;
2. **Запуск pipeline:** автоматическая обработка тестовых видео системой;
3. **Расчёт метрик:** сравнение извлечённых вопросов с экспертной разметкой;
4. **Анализ ошибок:** классификация причин пропущенных и ложных вопросов.

### 4.4.2. Метрики качества

Для оценки используются стандартные метрики информационного поиска:

$$Precision = \frac{TP}{TP + FP}$$

$$Recall = \frac{TP}{TP + FN}$$

$$F_1 = 2 \cdot \frac{Precision \cdot Recall}{Precision + Recall}$$

где:
- $TP$ (True Positive) — вопросы, корректно извлечённые системой (присутствуют в экспертной разметке);
- $FP$ (False Positive) — ложноизвлечённые вопросы (отсутствуют в экспертной разметке);
- $FN$ (False Negative) — пропущенные вопросы (присутствуют в экспертной разметке, но не извлечены системой).

Сопоставление считается корректным (True Positive), если нормализованное расстояние Левенштейна между извлечённым и экспертным вопросом не превышает 0.4 или косинусное сходство эмбеддингов превышает 0.75.

Дополнительно оценивается точность определения таймкодов:

$$MAE_{timecode} = \frac{1}{|TP|} \sum_{i \in TP} |t_i^{extracted} - t_i^{expert}|$$

### 4.4.4. Анализ ошибок

**Причины False Positive:**
1. Риторические вопросы кандидата, ошибочно определённые как вопросы интервьюера (32% FP);
2. Уточняющие фразы, не являющиеся полноценными вопросами: «Это понятно?», «Согласен?» (28% FP);
3. Вопросы из контекста обсуждения, не относящиеся к проверке знаний (40% FP).

**Причины False Negative:**
1. Вопросы, заданные неявно (утвердительная форма): «Расскажите про...», «Объясните...» (45% FN);
2. Цепочки связанных вопросов, объединённые LLM в один (30% FN);
3. Вопросы, потерянные при ошибках транскрибации (25% FN).

**Влияние гибридной транскрибации.** Сравнение результатов с использованием только Whisper vs. гибридный режим (Whisper + субтитры) показало:
- Precision: +3% при наличии субтитров (лучшая разметка ролей);
- Recall: +5% при наличии субтитров (меньше ошибок транскрибации);
- F1: +4% в среднем.

**Влияние LLM-провайдера.** Тестирование на одном видео с разными провайдерами:

| Gemini | gemini-2.0-flash | 0.76 | Иногда объединяет близкие вопросы |
| Groq | Llama-3.1-70B | 0.78 | Аналогично OpenRouter, выше latency |
