# 2 МЕТОДЫ И ТЕХНОЛОГИИ РЕШЕНИЯ ЗАДАЧИ

## 2.0 Постановка практической задачи главы

На основании требований к системе подготовки к IT-собеседованиям и замечаний из документа «РАбота над ошибками.docx» целевая система должна обеспечивать:

- поиск вопросов по технологии и теме;
- фильтрацию по уровню сложности;
- расширяемую фильтрацию по компании и региону;
- сортировку (вероятность, дата, алфавит и другие режимы);
- формирование списка вопросов с ссылками на источники;
- переход к фрагменту видео по таймкоду;
- расчет статистики частоты встречаемости вопросов;
- сохранение вопросов в избранное и ведение пользовательских заметок.

С математической точки зрения система реализует отображение:

$$
F: V \rightarrow Q
$$

где $V$ - множество видеоисточников, $Q$ - множество структурированных вопросов с метаданными.

Для каждого видео $v \in V$ формируется набор:

$$
Q_v = \{(q_i, t_i, m_i)\}_{i=1}^{n_v}
$$

где $q_i$ - текст вопроса, $t_i$ - таймкод, $m_i$ - метаданные (тема, сложность, источник, вероятность и др.).

## 2.1 Общая архитектура и этапы обработки видео

В реализованной архитектуре используется четырехэтапный pipeline:

1. извлечение аудио и субтитров из видео;
2. автоматическая транскрипция речи (ASR);
3. извлечение вопросов из текста (LLM + постобработка);
4. сохранение в БД и пересчет статистик.

Ключевая реализация pipeline:

- backend/main_new.py (функция process_video_pipeline)
- backend/video_downloader.py
- whisper-service/main.py

### 2.1.1 Извлечение аудиодорожки и субтитров

Для загрузки используется yt-dlp с мультиплатформенной поддержкой (YouTube, VK, Rutube, OK, Dailymotion, Vimeo). На выходе формируется:

- аудиофайл (обычно mp3);
- метаданные видео (title, duration, platform, url);
- субтитры VTT (если доступны).

Формально этап можно задать как:

$$
E(v) = (a_v, s_v, meta_v)
$$

где $a_v$ - аудиосигнал, $s_v$ - субтитры, $meta_v$ - метаописание видео.

Практические особенности реализации:

- отдельные профили загрузки для платформ с нестабильной доставкой;
- таймауты, ретраи, ограничение размера файлов;
- извлечение platform/video_id для унификации хранения.

### 2.1.2 Транскрипция аудио (ASR)

Транскрибация выполняется в отдельном сервисе whisper-service на faster-whisper (CTranslate2). Используется модель класса large-v3-turbo (русский язык, техническая речь), поддерживаются CPU и CUDA режимы.

Транскрипция возвращает:

- полный текст $T_v$;
- сегменты $S_v = \{(b_j, e_j, text_j)\}$, где $b_j, e_j$ - начало и конец сегмента.

Математически:

$$
ASR(a_v) = (T_v, S_v)
$$

где качество ASR может оцениваться метрикой WER:

$$
WER = \frac{S + D + I}{N}
$$

$S$ - замены, $D$ - удаления, $I$ - вставки, $N$ - число слов в эталоне.

### 2.1.3 Слияние транскрипции и субтитров

В системе реализуется гибридный подход: база сегментации берется из субтитров (когда доступны), а пунктуация/уточнения - из ASR-сегментов.

Пусть есть два сегмента:

- $u_k$ из субтитров;
- $w_j$ из Whisper.

Для сопоставления используется временная близость:

$$
\Delta_{k,j} = |t(u_k) - t(w_j)|
$$

Если $\Delta_{k,j} < \tau$ (в реализации пороговая эвристика порядка 2 секунд), сегменты считаются парой-кандидатом.

Итоговый объединенный сегмент:

$$
m_k = merge(u_k, w_{j^*})
$$

где $j^* = \arg\min_j \Delta_{k,j}$.

Практический эффект:

- повышается структурность текста;
- улучшается извлечение вопросительных конструкций;
- сохраняется привязка к таймкодам.

## 2.2 Сравнение и выбор технологии транскрипции

### 2.2.1 Кандидаты ASR

Для задачи русскоязычных IT-собеседований типично сравниваются три группы решений:

1. облачные API (закрытые провайдеры);
2. локальные легковесные модели (например, Vosk-класс);
3. крупные end-to-end модели класса Whisper.

### 2.2.2 Критерии выбора

Введем критерии:

- $C_1$ - точность распознавания терминологии;
- $C_2$ - устойчивость к шуму и разговорной речи;
- $C_3$ - воспроизводимость и автономность (локальный запуск);
- $C_4$ - стоимость обработки;
- $C_5$ - скорость на доступном железе.

Интегральный критерий:

$$
J = \sum_{i=1}^{5} w_i C_i, \quad \sum w_i = 1
$$

При приоритете качества для диссертационной задачи берутся повышенные веса на $C_1, C_2, C_3$.

### 2.2.3 Обоснование выбора faster-whisper

Выбрана связка faster-whisper + large-v3-turbo, так как она обеспечивает:

- высокую точность на разговорной речи с техническими терминами;
- локальную и контролируемую обработку;
- приемлемое время выполнения на CPU/GPU;
- сегментированный вывод, удобный для последующего NLP.

Именно поэтому в реальной реализации используются:

- whisper-service/main.py
- backend/services/whisper_orchestrator.py

## 2.3 Выделение вопросов из размеченного текста

### 2.3.1 Формулировка задачи извлечения

После транскрипции требуется выделить только вопросы интервьюера, исключив:

- ответы кандидата;
- риторические конструкции;
- «мусорные» короткие фразы.

Формально:

$$
G(T_v) = \hat{Q}_v
$$

где $\hat{Q}_v$ - множество извлеченных кандидатов вопросов.

### 2.3.2 LLM-извлечение

Используется LLM-промпт с принудительным JSON-форматом результата:

$$
\hat{q}_i = (text_i, topic_i, difficulty_i, timecode_i)
$$

Провайдер выбирается каскадно (OpenRouter/Gemini/Groq) по доступности ключей.

### 2.3.3 Постобработка качества

#### Фильтрация низкокачественных фраз

Вводится предикат качества:

$$
f_{qual}(q) =
\begin{cases}
1, & len(q) \ge L_{min} \land q \notin \mathcal{G}\\
0, & \text{иначе}
\end{cases}
$$

где $\mathcal{G}$ - набор регулярных шаблонов мусорных реплик.

#### Лексическая дедупликация

Нормализованная форма строки:

$$
norm(q) = lower(strip\_punct(q))
$$

Внутри одного документа дубликаты удаляются по множеству $Seen = \{norm(q)\}$.

#### Межвидео дедупликация в БД

В БД реализована проверка по нижнему регистру перед вставкой вопроса. Если вопрос уже существует, создается только связь с новым видео в question_video.

## 2.4 Хранение данных и модель базы знаний

### 2.4.1 Основные сущности

Для решения задачи построена реляционная модель, в которой ключевые таблицы:

- questions - вопрос, тема, сложность, вероятность, базовый таймкод;
- processed_videos - информация об источнике видео;
- question_video - связь многие-ко-многим вопрос-видео;
- question_timecodes - таймкод вопроса в конкретном видео;
- bookmarks и user_notes - пользовательская персонализация.

### 2.4.2 Вероятностная статистика вопроса

Пусть:

- $N_v$ - число всех обработанных видео;
- $n_i$ - число различных видео, где встретился вопрос $q_i$.

Тогда эмпирическая вероятность:

$$
P(q_i) = \frac{n_i}{N_v} \cdot 100\%
$$

Именно эта величина используется для ранжирования приоритета подготовки.

### 2.4.3 Таймкод как функция навигации

Для каждого вопроса в каждом видео хранится:

$$
TC(q_i, v_j) = (hh:mm:ss, sec)
$$

где sec - числовой эквивалент для быстрых переходов и сортировки.

## 2.5 Поиск, фильтрация, сортировка и навигация

### 2.5.1 Поисковая модель

Система использует два режима поиска:

1. метаданные и SQL-фильтры;
2. семантический поиск похожих вопросов (embeddings + FAISS).

#### SQL-фильтрация

Доступные фильтры в текущей реализации:

- topic;
- difficulty;
- profession (через profession_topics).

Сортировки:

- по вероятности;
- по дате;
- по алфавиту.

#### Семантический поиск

Векторы нормализуются по $L_2$, используется косинусная близость через inner product:

$$
sim(x, y) = \frac{x^T y}{||x||\,||y||}
$$

На практике применен IndexFlatIP (точный поиск top-k).

### 2.5.2 Формирование списка ссылок на ресурсы

Каждый вопрос в детальной карточке снабжается списком видео-источников:

$$
R(q_i) = \{(v_j, url_j, tc_{ij})\}
$$

Это обеспечивает прямой переход пользователя к месту в видео, где вопрос обсуждается.

### 2.5.3 Просмотр видеофрагмента по таймкоду

Переход к фрагменту строится как функция:

$$
U(url, sec) = url + "?t=" + sec
$$

(или эквивалентный формат для конкретной платформы).

### 2.5.4 Требуемые расширения: компания и регион

В требованиях главы 1 явно присутствуют фильтры по компании и региону. В текущей версии системы эти поля для банка вопросов выражены неполно.

Рекомендуемое расширение схемы:

- company (в вопросе или в таблице вопрос-источник);
- region (видеоисточник или вакансия-источник);
- индексы по (topic, difficulty, company, region, created_at).

Тогда общий фильтр:

$$
\mathcal{F} = (topic, difficulty, company, region, date\_range)
$$

а результат:

$$
Q_{out} = \{q \in Q : q \models \mathcal{F}\}
$$

## 2.6 Избранное и заметки как персонализирующий слой

Пусть $u$ - пользовательская сессия.

Избранное задается множеством:

$$
B_u = \{q_i\}
$$

Заметки:

$$
N_u = \{(q_i, note_i, t_i)\}
$$

Функции слоя персонализации:

- быстрый возврат к важным вопросам;
- фиксация собственных формулировок и подсказок;
- повышение повторяемости обучения.

С точки зрения обучения это уменьшает время доступа к «высокоценным» элементам:

$$
T_{access}^{personalized} < T_{access}^{global}
$$

## 2.7 Математические метрики качества системы

### 2.7.1 Качество извлечения вопросов

При наличии экспертной разметки используются:

$$
Precision = \frac{TP}{TP + FP}
$$

$$
Recall = \frac{TP}{TP + FN}
$$

$$
F_1 = 2\cdot\frac{Precision\cdot Recall}{Precision + Recall}
$$

### 2.7.2 Качество поиска

Для семантического поиска:

- Precision@k;
- Recall@k;
- MRR;
- nDCG@k.

### 2.7.3 Надежность вероятностной оценки

Для частоты вопроса можно учитывать доверительный интервал для доли:

$$
\hat{p}_i = \frac{n_i}{N_v}
$$

С ростом $N_v$ дисперсия оценки убывает:

$$
Var(\hat{p}_i) = \frac{\hat{p}_i(1-\hat{p}_i)}{N_v}
$$

Следовательно, при расширении корпуса видео ранжирование становится устойчивее.

## 2.8 Поэтапный алгоритм (в формате из задания)

Ниже приводится требуемый алгоритм в терминах реальной реализации.

### Шаг 1. Извлечение аудиозаписи из видеоматериала

- вход: URL видео;
- инструмент: yt-dlp;
- выход: аудиофайл + метаданные.

### Шаг 2. Транскрипция аудиосигнала

- вход: аудиофайл;
- инструмент: faster-whisper (large-v3-turbo);
- выход: текст + сегменты с временными границами.

### Шаг 3. Извлечение субтитров

- вход: видеоисточник;
- выход: VTT-субтитры (если доступны);
- примечание: при отсутствии субтитров используется только ASR.

### Шаг 4. Объединение результатов шагов 2 и 3

- сопоставление по временным меткам;
- выбор более информативной текстовой формы (с учетом пунктуации);
- выход: объединенные сегменты для NLP.

### Шаг 5. Выделение фраз-вопросов

- LLM-извлечение с JSON-контрактом;
- присвоение темы и сложности;
- извлечение/нормализация таймкодов;
- фильтрация мусорных и дублирующих фраз.

### Шаг 6. Сохранение и индексирование

- запись новых вопросов в БД;
- формирование связей вопрос-видео;
- сохранение таймкодов;
- пересчет вероятности вопроса;
- обновление семантического индекса.

## 2.9 Итоговое сравнение процедур и выбор технологий

По результатам анализа и практической проверки для системы выбраны:

1. **Извлечение видео/аудио:** yt-dlp (мультиплатформенность и устойчивость).
2. **ASR:** faster-whisper large-v3-turbo (баланс точности и скорости, локальный запуск).
3. **Извлечение вопросов:** LLM с жестким JSON-контрактом + регуляризованная постобработка.
4. **Семантический поиск:** sentence-transformers all-MiniLM-L6-v2 + FAISS.
5. **База знаний:** PostgreSQL + реляционные связи question-video-timecode.
6. **Оперативное состояние задач:** Redis + WebSocket для realtime мониторинга.
